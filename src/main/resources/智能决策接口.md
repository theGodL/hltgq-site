### 通用约定（前端必读）

| 约定 | 说明 |
|------|------|
| 鉴权 | 所有接口走登录会话（`Authorization` 头），公共库 `lib/model-api.js` 已统一处理，无需额外传参 |
| 异步轮询 | 计算类接口提交**秒回 recordId** → 轮询 status → completed 后拉详情。status 枚举：`calculating / completed / failed`；轮询可直接复用 `ModelApi.waitCompleted` |
| null 语义 | 图表序列中 `null` = 无数据：柱状图不画柱、折线断线；**不渲染为 0** |
| 百分数 | `patrolCompliance / issueCompliance` 返回 **0~100 数值**（如 `85.5` 表示 85.5%），前端拼接 `%` 展示，不做除法 |
| 数字精度 | 瞬时流量 3 位小数、水位 2 位小数、雨量 2 位小数（均截断补零）；含水率 2 位小数截断补零；方案汇总字段（totalDemand 等）为浮点可能带小数，展示用 `fmtNum` 处理 |
| 新接口封装 | 建议在 `lib/model-api.js` 补充 floodDrought / networkDevice / engineering / decision.branches 客户端（参考现有 `operation`、`soilMoisture` 写法），或页面内直接 `getJson('/xxx')` |

## 一、网络设备监控

一次请求渲染整页：顶部汇总卡 + 7 类设备列（水位/雨量/流量/闸门/视频/墒情/水质）+ 未分类提示。

**统计对象是「设备」（设备台账，一台算一台），不是「站点」**：`total` = 设备台账全部行 = `Σcategories[].total` + `uncategorized`，业主按分类相加能对上总数。

```
GET /network-device/summary
```

无参数。

### 1.1 响应

> 下例为 2026-09-23 全库实测（`categories` 仅列 1 项示例，实际固定返回 7 项）：

```json
{
  "regionName": "花凉亭灌区",
  "total": 357,
  "uncategorized": 9,
  "summary": {
    "online":  { "count": 299, "percent": 83.75 },
    "offline": { "count": 58,  "percent": 16.25 },
    "alarm":   { "count": 108, "percent": 30.25 },
    "fault":   null
  },
  "categories": [
    {
      "key": "gate",
      "name": "闸门",
      "color": "#6B3FDD",
      "icon": "gate",
      "total": 51,
      "counts": { "online": 46, "offline": 5, "alarm": 1, "fault": null },
      "devices": [
        { "id": "设备ID", "name": "双庙湖节制闸1#", "status": "online" },
        { "id": "设备ID", "name": "双庙湖节制闸2#", "status": "offline" }
      ]
    }
  ]
}
```

### 1.2 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| regionName | String | 区域名 |
| total | Number | **设备总数**（设备台账全部行，一台算一台）= `Σcategories[].total` + `uncategorized`；与 `/dashboard/overview` 的 `totalDeviceCount` 同源同值 |
| uncategorized | Number | **未分类设备数**（台账未维护 `type`、或 `type` 不含 7 类编码的设备，如北干渠/南干渠/汪元节制闸闸孔、建设支渠、待接入等）；不计入任何分类，台账补上类型后自动归入对应分类 |
| summary.* | Object | `online` / `offline` / `alarm` 必返回 `{count,percent}`；**`fault` 恒为 `null`**（告警表无故障维度、设备台账无故障标识，暂无数据源 → 前端不展示该项，不再用假 0 代替） |
| summary.alarm | Object | **告警设备台数**：设备存在未关闭告警（告警表 `status` ∈ `#1#`/`#2#`/`#3#`，同一台设备多条告警只算 1 台）即计入；与大屏 `/dashboard/overview` 的 `unhandledAlarmCount` **同表同过滤**，差别只在单位（大屏算告警条数、本接口算台数）。`percent` 分母 = 设备总数 |
| summary.*.percent | Number | 保留两位小数（HALF_UP，与 `/dashboard/overview` 同一规则），直接展示拼 `%`（如 `83.75`） |
| categories[] | Array | **固定 7 项、顺序固定**：waterLevel/rainfall/flow/gate/video/soil/quality；设备表无数据时仍返回 7 项（全 0 结构，页面不会塌） |
| categories[].total | Number | 该分类设备数（**唯一归属**：一台设备只归入一个分类，`type` 多值如 `#1#\|#2#` 取首个命中分类的编码） |
| categories[].counts | Object | 分类内计数：`online`+`offline` = 该分类总数；`alarm` = 该分类内告警设备台数（与在线/离线正交，可同时计入）；`fault` 恒为 `null`（不展示） |
| categories[].color / icon | String | 分类色块色值与图标键名，页面渲染**直接使用**（`cat.color`、`ICONS[cat.icon]`），不要自行映射 |
| devices[] | Array | 该类**全量**设备；`status` 仅 `online/offline` 两种取值 |
| devices[].status | String | 在线判定口径：**设备表 `status` 有值时以自身为准**（mq 报文入库时维护全部设备状态），**为空时回退该设备所属站点档案 `zebpsu`**（`#1#` 在线 / `#2#` 离线，与大屏 `/dashboard/overview`、水位页 `isOnline` 同源）；两处均无值或未知编码 → `offline` |
| devices[].id / name | String | 设备 ID（唯一）/ 名称（格式「站点名+闸孔号#」或「站点名+设备类型#」） |

> **状态来源说明（2026-09-23 mq 改造后实测）**：设备运行状态取自设备表 `t_auto_hltgq_water_device.status`，由 mq 报文入库时维护——**全库 357 台设备均已有值、无空值**（取值仅 `#1#` 在线 / `#2#` 离线）。设备 `status` 为空时（如新接入设备尚未回写）接口自动回退该设备所属站点档案 `zebpsu`（关联：设备表 `site` → 站点档案表 `id`），两处均无值或未知编码 → `offline`。2026-09-23 实测 **299/357 在线（83.75%）**（= 大屏 `onlineDeviceCount`）。数字随设备状态实时更新（同一库不同时刻会漂移几台），核对请两接口同一时刻同时取数。
>
> 后端每次构建会打口径核对日志：`网络设备状态口径：共 N 台，在线 X / 离线 Y；其中按站点 zebpsu 回退判定 Z 台；未分类（台账未维护类型）K 台；告警设备 M 台`（Z 为设备 `status` 为空的台数，K 应等于响应里的 `uncategorized`，M 应等于 `summary.alarm.count`）。
>
> **告警口径（2026-09-23 接入）**：`summary.alarm` 与各分类 `counts.alarm` 为**告警设备台数**——设备在告警表 `t_auto_hltgq_water_alert` 中存在未关闭告警（`status` ∈ `#1#` 未确认 / `#2#` 已确认 / `#3#` 处理中，`#4#` 已关闭不计）即计 1 台，同一台设备多条告警只算 1 台；分类内按设备**主类型唯一归属**统计（未分类设备不计入任何分类），故分类相加与汇总同源（当前 Σ分类 `counts.alarm` = `summary.alarm.count` = 108）。实测 108/357（30.25%）：视频 89 台、流量 18 台、闸门 1 台。
>
> **与大屏 `unhandledAlarmCount` 的关系（业主核对必读）**：同表、同一过滤条件，**差别只在单位**——大屏按**告警条数**（实测 120 条），本接口按**设备台数**（实测 108 台）。差额可逐条对上：① 同一台设备多条告警 7 条（视频 96 条落在 89 台上）；② 台账无档案的设备 4 条（均为测试站点，如「水位测试站点0909 连续24小时未收到任何报文」）；③ 站点级告警 1 条（`device` 为空，无法归属到设备）。即 120 = 115（108 台台账设备）+ 4 + 1。
>
> **故障（`fault`）**：告警表无故障维度（`level` 是告警等级、`type` 是告警类型）、设备台账无故障标识，**暂无数据源**，接口返回 `null`、页面不展示该项（不再用恒 0 冒充）；若后续有故障数据源（如设备故障抢修工单）再接入。告警查询异常时降级为 0 并打 `warn` 日志（不影响在线/离线与分类统计）。
>
> 结果有 Redis 缓存 60s（key `decision:network-device:summary`），调整口径后需等缓存过期或清 key 才可见新结果。

> **统计对象说明（2026-09-23，业主核对对号表）**：本接口统计的是**设备**（设备台账，实测 357 台），与**站点**（站点档案，实测 368 个）不是一个概念，两者数量本就不相等。
>
> | 数字 | 统计对象 | 来源 | 实测值 |
> |------|---------|------|--------|
> | `total` | 设备（一台算一台） | 设备台账 `t_auto_hltgq_water_device` | 357 = 各分类 348 + 未分类 9 |
> | `summary.online.count` | 设备 | 设备 `status` 优先、空回退所属站点 `zebpsu` | 299（83.75%） |
> | `summary.alarm.count` | 设备 | 告警表未关闭告警（`#1#`/`#2#`/`#3#`）去重台数 | 108（30.25%） |
> | `categories[gate].total` | **闸孔设备**（同站 1#/2#/3# 各算一台） | 设备台账 `type` 含 `#4#` | 51（补录后 58） |
> | 大屏 `totalGateCount` / `openGateCount` | **闸孔设备**（与本接口闸门分类同一对象） | 设备台账 `type` 含 `#4#` | 51 / 开启 21（补录后 58 / 28） |
> | 大屏 `totalDeviceCount` / `onlineDeviceCount` | 设备 | 与本接口完全同源 | 357 / 299 |
> | 大屏 `unhandledAlarmCount` | 告警**条数** | 告警表未关闭告警（同过滤） | 120 条（对应本接口 108 台） |
> | 站点在线数（口径参考，不属本接口） | **站点** | 站点档案 `zebpsu`（`#1#` 在线） | 267 / 368 |
>
> 上表为**台账补录前**实测；闸门台账补录 7 台 `type = #4#` 后：`categories[gate].total` 51 → 58、开启 21 → 28、各分类合计 348 → 355、`uncategorized` 9 → 2（`total` 仍为 357）。
>
> 即：`total` 必须等于大屏 `totalDeviceCount`、`summary.online.count` 必须等于大屏 `onlineDeviceCount`（同源实现，同一时刻取数必然相等）；本接口闸门分类与大屏 `totalGateCount` 是**同一对象**（设备台账 `type` 含 `#4#` 的闸孔设备，实测 51 台 / 开启 21），两处必然同值；本接口 `summary.alarm.count` 与大屏 `unhandledAlarmCount` 同表同过滤（大屏条数 / 本接口台数）。设备台数（299）与站点在线数（267）维度不同**不可相减**：站点在线是「站」维度（一个在线站下可有多台在线设备）；2026-09-23 mq 全量维护设备 `status` 后，站点与设备状态已完全一致（实测「设备全离线但站点在线」0 站、反向 0 站）。
>
> 9 台未分类设备（台账缺类型）：9999900001待接入#、**北干渠进水闸1#/2#**、**南干渠进水闸1#/2#**、**汪元节制闸1#/2#/3#**、建设支渠1#。其中 **7 台为闸孔设备**（近 24h 均有闸门上报、开度 > 0，闸门监测页已展示、但台账未标 `#4#` 而不计入闸门分类与大屏闸门数）：台账补 `type = #4#` 后闸门分类将变为 **58 台 / 开启 28**，与大屏、闸门监测页口径完全一致（补录清单见 `闸门设备台账补录清单.md`）。
>
> 监测页面（水位/雨量/流量/闸门/墒情）按采集时间超时标红是**缺测/断联**提示（MQTT 站 30 分钟、其余站 70 分钟无更新），与本接口/大屏的**在线离线**是两个概念，不参与统计。

### 2.2 历史实测块（同步查询，无轮询）

```
GET /flood-drought/history?startDate=2026-09-01&endDate=2026-09-05[&rainStcd=...&levelStcd=...&flowStcd=...]
```

参数：

| 参数 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| startDate | String | 是 | 起始日期 `yyyy-MM-dd`（含） |
| endDate | String | 是 | 截止日期 `yyyy-MM-dd`（含）；`endDate < startDate` → 400；区间 > 90 天 → 400 |
| rainStcd / levelStcd / flowStcd | String | 否 | 选站（取 2.1 下拉的 stcd）；不传时按配置，未配置按类型自动选站（水位默认花凉亭坝上 3206400007）；无效 stcd 该序列全 null |

响应：

```json
{
  "dates": ["2026-09-01", "2026-09-02", "2026-09-03", "2026-09-04", "2026-09-05"],
  "rain":  { "stcd": "3206400001", "stnm": "周家河", "values": [8.5, 18.2, null, 0.0, 3.1] },
  "level": { "stcd": "3206400007", "stnm": "花凉亭水库(坝上)", "values": [72.102, 68.531, 67.902, null, 68.120] },
  "flow":  { "stcd": "CAYQ739MiBWMg9gQvyi", "stnm": "渠首进水闸", "values": [42.0, 40.3, null, 39.5, null] }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| dates | String[] | 横轴逐日标签（含首尾，自然日） |

### 2.3 预测块（短期预报方案）

预测块复用 `/water-forecast/short` 接口，**两种取数方式**：

**方式一：本页按参数直接计算**（对应会议「按所选日期、降雨量、开关取最新结果」，推荐）

```
POST /water-forecast/short          body: { "start": "2026-09-05 08:00", "end": "2026-09-08 08:00", "enablePower": false, "enableTunnel": false, "enableSpillway": false, "rainfall": [...] }
      → { "recordId": "..." }（秒回）
GET  /water-forecast/short/status/{id}   → { "id", "status": "calculating|completed|failed", "errorMsg" }
GET  /water-forecast/short/{id}          → { "record": {...}, "dailies": [逐小时明细] }（仅 completed 后调用）
```

| 提交参数 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| start / end | String | 是 | 预报窗口 `yyyy-MM-dd HH:mm`（含端点，1~384 小时，对应前端所选日期） |
| enablePower / enableTunnel / enableSpillway | Boolean | 否 | 发电/泄洪隧洞/溢洪道开关，**默认均 false**（模型参数默认 true，后端按会议「默认全关」口径显式传 false；前端不传即全关） |
| rainfall | Number[] | 否 | 与窗口等长的逐小时降雨序列（前端所选降雨量）；不传则后端自动拉气象 |
| schemeName | String | 否 | 方案名称（默认自动生成） |

**方式二：下拉历史方案**（展示既往计算结果，不再提交）

```
GET /water-forecast/short/list   → 方案列表（含 id/schemeName/status/startDate/endDate 等，最新在前）
GET /water-forecast/short/{id}   → 同上详情
```

dailies[] 常用字段：

| 字段 | 说明 |
|------|------|
| forecastDate | 小时粒度时间（模型 data[].时间） |
| rainfall | 逐小时降雨（mm，模型入参） |
| waterLevel | 逐小时水位（m，模型演算） |
| inflowRate / outflowRate | 入/出库流量（m³/s） |
| inflowVolume / outflowVolume / storage | 入/出库水量、库容（万方） |

要点：

- 预测段取 `dailies` 按日聚合接入拼图（口径见 2.4：雨量和；水位/流量优先 08:00 值、否则当日最后值）

### 2.4 概览接口（2026-09-13 新增，进页面自动加载）

页面进页默认调用一次（毫秒级纯读取，**不触发模型**），实测段 + 预置预测段一次返回，首屏不再空图：

无参数。响应（与拼图渲染结构直接对齐）：


| 字段 | 类型 | 说明 |
|------|------|------|
| dates | String[] | 默认区间（今日-2 ~ 今日+12）逐日标签 |
| splitDate | String | 实测/预测分界日（= 今日；分界日两端共用实测点做视觉衔接） |

**预置预跑机制**（后端自动，前端无感）：定时任务每 **4 小时**一轮按窗口 `[明日 08:00, 今日+13 08:00]` 检查——无「计算中 / `refresh-hours`（默认 3h）内完成」的覆盖记录时自动提交一次（方案名前缀「智能防洪预置_」，参数与页面「计算」完全相同，模型异步 ~20s），保证上午/下午各时段进页看到的都是新一轮预测；新鲜记录直接复用，不做重复计算。概览取数**始终取最新可用已完成方案**（先给老数据、后台再刷新）——跨天过渡期昨日记录尚不覆盖今日窗口时仍按其完整覆盖的日先展示（`partial=true`，见上表），首屏不出现空预测；用户点「计算」提交的同窗口方案同样会被后续概览复用（越用越新）。超期预置方案按 `cleanup-hours`（默认 48h）自动软删，方案列表不被整日堆积。

**前端接入**：进页 `API.floodDrought.overview()` → `renderFloodCombo(payload)`（渲染结构与手动计算一致）；`predMeta` 按上表在标题右侧提示；概览请求失败时降级空态 + 提示点击「计算」；点「计算」期间保留已渲染图（不闪空），新结果返回后直接覆盖。
