# 数据统计（统计大屏对接文档）

本文档说明统计大屏各模块的数据来源归属：哪些由 hltgq-mq 提供、哪些需要 hltgq-site / hltgq-device 提供，
以及 hltgq-mq 能提供的接口、数据基础和口径，供前后端及跨系统调用方对接。

## 1. 背景与目标

统计大屏包含 5 个模块：

| 模块 | 内容 |
|---|---|
| 站点到报明细 | 站点名称/编号、报文类型（分钟报/整点报）、应到/实到/缺报次数、到报率、状态 |
| 缺测明细 | 站点、缺测时间段、缺测时长、数据类型、当前状态（缺测中/已恢复） |
| 服务监测 | mq 三逻辑服务（数据接收/解析/存储，同进程共享资源指标）的运行状态与指标 |
| 数据采集状态统计 | 水位/流量/雨量/闸门开度/墒情/视频的应采、实采、成功、失败、成功率（视频由 hltgq-device 巡检统计，见 7.1） |
| 信息发布情况 | 预警信息（本项目无发布操作，业务定稿：每次生成告警即发布；仅保留“预警信息”一行） |

> 模块口径演进（2026-09-09 业务拍板）：服务监测原原型 5 个逻辑服务（含信息发布/告警推送）收敛为 mq 三服务；
> 信息发布原原型 4 种发布类型（水情通报/调度指令/预警信息/日报周报）收敛为仅“预警信息”；采集维度原不含视频，当日另由 hltgq-device 巡检统计补入（见 7.1）。
> 上述收敛后，页面所有区块的数据均可由第 4 章接口覆盖。

## 2. hltgq-mq 数据基础（我们能提供的帮助）

hltgq-mq 是全量报文入口：RabbitMQ（每站约 1 小时一批，每批 4 个 tag）+ MQTT（四闸站每 10 分钟一条 payload）
均在本项目完成接收、解析、守卫、入库，因此**"报文字段级"的权威数据都在本项目**。

### 2.1 报文流水 msg_info（到报事实）

`"qixiao-apaas"."t_auto_hltgq_water_msg_info"`：每条报文一行，**守卫前统一留痕**（被拦截的异常报文同样留痕，
如 -999 流量：链路通、设备有上报即算到报）。

| 列 | 语义 |
|---|---|
| site | 站点 ID |
| device | 设备 ID（RabbitMQ=该站 RTU 设备；MQTT=闸孔 1# 设备） |
| stcd | 测站编码（MQTT 无 stcd 留空） |
| tm | 入库时间（服务器时间） |
| sendtm | 设备发送时间（优先报文 SendTM，缺失/异常退业务 TM，再兜底入库时间） |
| afn | 功能码（无则留空） |
| msg | 报文标识（msgInfo 取 MSG 文本，其他 tag 取 tag 名；MQTT 取站点前缀 NSS/QSDZ/QSJSZ/SMH） |
| msg_text | 原始报文 JSON 全文（不加工、不合并） |

### 2.2 业务数据表（有效数据事实）

有效数据按站点类型主监测要素判定（哨兵值 -999/-9991 等不算有效）：

| 数据类型 | 表 | 有效条件 |
|---|---|---|
| 水位 | t_auto_hltgq_water_river_info | `z > 0` |
| 雨量 | t_auto_hltgq_water_rain_info | `dyp > 0`；晴天 DYP=0 不入库，按"该窗有 rainInfo 报文"算有效观测 |
| 流量 | t_auto_hltgq_water_wt_nfo | `q >= 0` |
| 墒情 | t_auto_hltgq_water_nmisp_info | `mten >= 0` |
| 闸门开度/闸站水位 | t_auto_hltgq_water_gate | `up_z > 0 OR down_z > 0 OR open_degree >= 0` |

### 2.3 其他可提供的数据

- 站点档案（站点表 `t_auto_hltgq_5nw74_vnqqef`：站名 zzkaec、stcd iofhpi、类型 epjutj）
- 告警记录（alert 表：失联/超限告警生成在本项目，告警工单联动字段齐全）
- 站点在线/离线状态（基于报文 updated_at 判定，与离线判定同口径）
- 召测能力（POST /api/recall，四站白名单，同步等待应答入库）

## 3. 统计口径（基础定义）

**报到（通信层）**：有报文就算到报。雨量站 4 小时窗（RTU 无雨 4h 一报、有雨加密）、
RabbitMQ 站 1 小时窗、MQTT 闸站 10 分钟窗。

**缺测（数据层）**：有报文但数据有效并入库才算正常，否则缺测；完全没报文也算缺测。
雨量站 4 小时窗、RabbitMQ 站 1 小时窗、MQTT 闸站 30 分钟窗（对齐 gate 表 30 分钟批量入库节奏）。

**应报/应测窗数**：只统计当日 0 点至当前时刻**已结束的完整窗**（进行中的窗不计，未来时段不摊薄分母）。
到报率 = Σ各站到报窗 ÷ Σ各站应报窗（按站粒度加权）。
缺测率 = Σ各站缺测窗 ÷ Σ各站应测窗（仅参与缺测判定的站点，与到报率分母不同，两者不互为补数）。

**报文类型**：分钟报 = MQTT 四闸站（南山寺节制闸/渠首电站防洪闸/渠首进水闸/双庙湖节制闸）；
整点报 = RabbitMQ 站。

**参与统计的站点全集**：有 stcd 且（有设备档案 或 本月有报文流水）的遥测站，或有 gate 数据的 MQTT 闸站；
剔除测试站（站名含"测试"或 stcd 以 9999 开头）。新建档未接设备的渠道站不计应报，避免拉低到报率。

**月均口径**：从流水上线日（statStartDate）起逐日平均，跨月后统计窗口跟随本月 1 日；
statStartDate 默认自动取 msg_info 表 msg_text 非空首日，可用配置 `stats.start-date=yyyy-MM-dd` 覆盖。
接口响应的 statStartDate 字段输出的是**本月实际统计起始日**（=max(流水上线日, 本月 1 日)，跨月后为当月 1 日）。

**参与站点可选排除**：渠道站（如召测渠道站 9000000xxx）如需整体不参与统计，配置
`stats.exclude-stcd-prefix=9000000` 即可（默认空=不排除）；剔除动作在日志可见。

## 4. 接口清单（hltgq-mq 能实现的）

### 4.1 已实现

**GET /api/report/arrival-stats**（统计卡片聚合）

```json
{
  "code": 0,
  "data": {
    "stationTotal": 130,           // 参与统计的站点总数（已剔除测试站/无设备无流水站，KPI站点总数直接用此值；与 arrival-detail 行数一致）
    "todayArrivalRate": 74.46,     // 今日到报率(%)
    "monthAvgArrivalRate": 74.46,  // 本月平均到报率(%)，从流水上线日起逐日平均
    "todayMissRate": 19.68,        // 今日缺测率(%)=Σ缺测窗÷Σ应测窗(仅参与缺测判定的站点，与到报率分母不同)
    "statStartDate": "2026-09-09",  // 本月实际统计起始日（=max(流水上线日,本月1日)，跨月后为当月1日）
    "noReportSites": [              // 今日未到报站点（示例：全天 0 报的渠道站，真实停报）
      { "siteId": "...", "siteName": "周家河", "stcd": "3206400001" }
    ],
    "missedSites": [                // 今日缺测站点
      { "siteId": "...", "siteName": "...", "stcd": "...",
        "lastValidTm": "2026-09-09 08:00:00", "missedWindows": 3, "missRate": 12.5 }
    ]
  }
}
```

结果 60 秒内存缓存（五个接口共享同一统计上下文缓存，高频轮询不重复打库）；错误时 `code=1` 且 `msg` 说明原因。

### 4.2 已实现（四个明细/状态接口）

**GET /api/report/arrival-detail**（站点到报明细，每站一行）

```json
{
  "code": 0,
  "data": [
    { "siteId": "...", "siteName": "周家河", "stcd": "3206400001",
      "msgType": "整点报",      // 分钟报=MQTT四闸站 / 整点报=RabbitMQ站
      "expected": 15,          // 应到次数（今日已结束完整窗数）
      "arrived": 14,           // 实到次数（有报文的窗数）
      "missed": 1,             // 缺报次数
      "arrivalRate": 93.33 }   // 到报率(%)；状态档位（正常/偏低/异常/未到报）由产品定阈值
  ]
}
```

**GET /api/report/miss-detail**（缺测明细，按缺测时间段展开，连续缺测窗合并为一段）

```json
{
  "code": 0,
  "data": [
    { "siteId": "...", "siteName": "...", "stcd": "...",
      "startTm": "2026-09-09 09:00:00",   // 缺测开始时间
      "endTm": "2026-09-09 12:00:00",     // 缺测结束时间（开区间）
      "missMinutes": 180,                  // 缺测时长(分钟)
      "dataTypes": ["水位"],               // 缺测的数据类型（水位/雨量/流量/闸门开度/墒情）
      "status": "缺测中" }                  // 缺测中=覆盖最近完整窗 / 已恢复=已有有效数据
  ]
}
```

**GET /api/report/collect-stats**（数据采集状态统计，按数据类型聚合）

```json
{
  "code": 0,
  "data": [
    { "dataType": "水位数据",
      "expected": 200,       // 应采（采集周期窗数：雨量站 4h / RabbitMQ 1h / MQTT 30min）
      "collected": 185,      // 实采（有报文的窗数）
      "success": 180,        // 成功（有效数据入库的窗数）
      "failed": 5,           // 失败（有报文但数据无效，如 -999）
      "successRate": 90.0,   // 成功率(%)=成功/应采
      "failRate": 2.5 }      // 失败率(%)=失败/应采
  ]
}
```

维度：水位数据/流量数据/雨量数据/闸门开度/墒情数据（视频归 site/device）；
雨量维度晴天 DYP=0 报文按有效观测计成功。

**自洽约束**：collected = success + failed 恒成立，success ≤ collected。
success 按“有报文且有有效数据的窗”交集计（报文 tm 与业务行 tm 的跨桶分钟偏差归入 failed）。

**GET /api/report/service-status**（mq 自身服务状态；信息发布统计由 site 的 publish-stats 提供）

```json
{
  "code": 0,
  "data": {
    "process": { "startTime": "2026-09-09 08:00:00", "uptimeMinutes": 340,
                 "cpu": 12.5, "memoryUsedMB": 320, "memoryMaxMB": 1024 },
    "services": [
      { "name": "数据接收服务", "status": "运行中", "todayRequests": 350, "successRate": 100.0 },
      { "name": "数据解析服务", "status": "运行中", "todayRequests": 350, "successRate": 100.0 },
      { "name": "数据存储服务", "status": "运行中", "todayRequests": 220, "successRate": 98.5 }
    ]
  }
}
```

说明：三逻辑服务同进程，进程指标共享；今日请求：接收/解析=今日报文条数（msg_info 行数，
MQTT 一条 payload 按 4 站拆 4 行），存储=今日各业务表入库行数（7 表合计，逐表容错）；
接收/解析 successRate 恒 100（MQ 至少一次投递语义，失败仅 WARN 日志未埋点计数）；
存储 successRate=有报文且有有效入库的窗÷有报文的窗（交集口径，≤100%）。

### 4.3 site 网关转发端点与前端对接（2026-09-09 联调定稿）

mq 统计接口仅内网可达、不对外暴露，前端统一调用 hltgq-site 网关 `/data-statistics/*`（站点根路径
`http://<site>/hltgq-site/data-statistics/*`，需登录会话）。site 对 mq 五接口按同名路径 1:1 转发，
透传 mq 响应 {code,msg,data} 中的 data 段；视频采集统计转 hltgq-device 巡检统计接口：

| site 端点（GET） | 转发目标 | data 结构 |
|---|---|---|
| /data-statistics/arrival-stats | mq /api/report/arrival-stats | 对象（KPI 卡片） |
| /data-statistics/arrival-detail | mq /api/report/arrival-detail | 数组（每站一行） |
| /data-statistics/miss-detail | mq /api/report/miss-detail | 数组（每缺测段一行） |
| /data-statistics/collect-stats | mq /api/report/collect-stats | 数组（每数据类型一行） |
| /data-statistics/video-collect | device /api/dahua/video/patrol-stats | 对象（视频数据一行） |
| /data-statistics/service-status | mq /api/report/service-status | 对象（process + services[]） |
| /data-statistics/publish-stats | site 本地（无转发） | 数组（预警信息一行） |

**/data-statistics/publish-stats（site 本地实现，业务拍板口径）**：

```json
{
  "type": "预警信息",        // 固定：仅此一种发布类型（水情通报/调度指令/日报周报不统计）
  "count": 154,              // 今日生成的告警数（告警表 t_auto_hltgq_water_alert，time >= 今日 0 点，含全部分级/处理状态）
  "ok": 154,                 // 生成即发布成功：恒 = count
  "fail": 0,                 // 无失败概念：恒 0
  "okRate": 100.0,           // 恒 100.0
  "latest": "2026-09-09 20:39:20",  // 今日最近一次告警生成时间（北京时间文本 yyyy-MM-dd HH:mm:ss）；当日无告警为 null
  "status": "正常"
}
```

**错误语义**：mq/device 不可达或返回失败时，site 统一 HTTP 502 `{"code":502,"message":"数据统计服务…"}`；
未登录 401。

**前端字段映射与渲染注意**（页面 data-statistics.html 原型字段 → 真实接口）：

1. KPI 卡：站点总数=stationTotal；今日到报率/本月平均到报率=todayArrivalRate/monthAvgArrivalRate（数字拼接 %）；
   未到报站点/今日缺测站点=noReportSites.length/missedSites.length；可展示 statStartDate（统计起始日）。
2. 到报明细：name/code→siteName/stcd；type→msgType；expected/actual/missing→expected/arrived/missed；
   rate→arrivalRate（%）。“状态”档位（正常/偏低/异常/未到报）mq 不输出，由前端按 arrivalRate 阈值渲染（建议 100/≥80/0~80/0）。
3. 缺测明细：period→由 startTm~endTm 截取时间拼；duration→missMinutes 换算（x小时x分）；
   dataType→dataTypes 数组（可多类型，如 ["水位","雨量"]，拼接展示）；status/详情弹窗字段同源直用。
4. 服务监测：表格行=services[]（3 行：数据接收/解析/存储）；启动时间/运行时长/CPU/内存取 process 共享指标
   （三服务同进程）；successRate 恒有值（接收/解析=100，存储≤100）。信息发布/告警推送服务行不存在，不再渲染。
5. 采集统计：expect/actual/ok→expected/collected/success；collected=success+failed 恒成立；
   表格 = mq collect-stats 5 行 + /data-statistics/video-collect 1 行（device 视频巡检统计，见 7.1；
   视频行缺失时自动省略）。
6. 信息发布：渲染 publish-stats 返回行（仅预警信息）；无告警时 count=0、latest=null（展示 -- 由前端决定）。
7. 日期控件：统计口径固定“今日/本月”（已结束完整窗），接口无历史日期参数，原型日期选择仅作 UI（或由前端隐藏），
   不支持历史区间查询；跨日后自然滚动。
8. 分页/导出/详情弹窗：数据全量返回（站点 ≤130 行、缺测段 ≤101 段量级），分页与导出在浏览器端完成即可。

### 7.1 视频数据采集统计方案（已实施，2026-09-09 device 代码落地、留痕表已建）

**需求来源**：统计大屏“数据采集状态统计”区块 mock 含“视频数据”行
（expect/actual/ok/fail/okRate/failRate；量级 expect=720≈15 通道 × 48 窗/天）。
采集语义 = **视频通道周期巡检**（非录像/云台/IVSS 事件——那些不是周期采集）。

**实施路径（已落地）**：VideoAlertScheduler 已按 `video-alert.cron`（默认每 30 分钟一轮）巡检全部视频通道
（登录检查→通道池构建→并发抽帧质检→防抖→告警入库）；本轮新增巡检留痕落库与统计接口，改动集中在
VideoAlertScheduler doRound 收尾 + VideoPatrolRecordService（落库/聚合）+ VideoPatrolStatsController。

**① 巡检留痕表**（共享库 `qixiao-apaas`，device JdbcTemplate 直连写入，人大金仓，✅ 已建）：

```sql
CREATE TABLE "qixiao-apaas".t_auto_hltgq_water_video_patrol (
  id           VARCHAR(64)  NOT NULL,
  corp_code    VARCHAR(16)  DEFAULT 'hltgq',
  round_time   TIMESTAMP    NOT NULL,   -- 轮实际开始时间（统计按落入的 30min 窗计数）
  channel_code VARCHAR(64)  NOT NULL,   -- 通道 devicecode（如 1000231$1$0$10）
  result       VARCHAR(8)   NOT NULL,   -- ok=正常 fail=检出故障 error=检测异常
  fault_types  VARCHAR(255),            -- 故障枚举名逗号分隔（result=fail 时有值，否则为空）
  created_at   TIMESTAMP,
  created_by   VARCHAR(64),
  CONSTRAINT pk_video_patrol PRIMARY KEY (id),
  CONSTRAINT uk_video_patrol_round UNIQUE (round_time, channel_code)  -- 幂等重跑防重
);
CREATE INDEX idx_video_patrol_round ON "qixiao-apaas".t_auto_hltgq_water_video_patrol (round_time);
```

- 每轮巡检收尾逐通道 INSERT（复用每轮已算出的检测结果，`ON CONFLICT (round_time, channel_code) DO NOTHING` 幂等）；
- 离线通道=直接判信号丢失候选（现状如此），本轮结果按对应故障类型落库（result=fail + fault_types 枚举名）；
- 检测异常/超时通道落 result=error（与防抖口径独立；failed 含此类，对应 mq“有报文但数据无效”语义）；
- 表量级：15 通道 × 48 轮/天 ≈ 720 行/天，一年约 26 万行，无压力；
- id 复用现有 IdGenerator（20 位随机串，与站点表同规则）；result 三态化：原草拟将故障枚举名混存 result，最长的 PTZ_OUT_OF_CONTROL（18 字符）会超出 VARCHAR(16)，故拆为三态 result + fault_types 明细。

**② 统计口径（与 mq collect-stats 完全同构，避免大屏两口径打架）**：

| 字段 | 定义 |
|---|---|
| dataType | 固定“视频数据” |
| expected 应采 | Σ参与统计视频通道数 × 当日已结束完整 30min 窗数（进行中窗不计，同 mq 完整窗规则；参与通道 = 站点表视频站点（epjutj 含 #5#）devicecode 去重，与站点同步口径一致） |
| collected 实采 | 留痕中当日已结束窗内的通道窗数（result 为 ok/fail/error 均算，即实际完成检测；与 expected 同窗界，不会超分母） |
| success 成功 | result=ok 的通道窗数 |
| failed 失败 | result=fail+error 的通道窗数（故障类型 + 检测异常/超时；对应 mq“有报文但数据无效如 -999”语义） |
| successRate | success ÷ expected × 100（%）；failRate = failed ÷ expected × 100 |

- 整轮跳过（登录失败/设备树遍历不完整/轮级异常）当轮无留痕 → collected 少、successRate 自然下降（与 mq 断网期同语义），不另造补偿行；
- 防抖（连续 N 轮故障才告警）属告警层，**统计层不过防抖**，按每轮原始结果计数；
- IVSS 智能事件、录像月状态、云台操作均不参与本统计。

**③ device 统计接口**（GET，返回单行对象与 mq collect-stats 行同结构）：

```json
GET /api/dahua/video/patrol-stats        // 当日 0 点起，实时聚合
响应 data（site 透传）：
{ "dataType": "视频数据", "expected": 720, "collected": 715,
  "success": 703, "failed": 12, "successRate": 97.6, "failRate": 1.7 }
```

- 实现：JdbcTemplate 当日聚合（留痕表 COUNT group by result，round_time 限定 [当日0点, 已结束窗上界)，
  与 expected 同窗界，避免“进行中窗已留痕”造成 collected>expected）；
  窗长取配置项 `video-alert.patrol-window-minutes`（默认 30，与 video-alert.cron 轮次间隔保持同步）；
- expected 分母（参与通道数）实时查站点表视频站点计数（与统计聚合同口径筛 epjutj 含 #5#），无缓存漂移；
- 查询失败降级返回 0 值不抛异常（大屏不中断）；720 行级聚合毫秒级，无需缓存；鉴权与会话与 device 现有接口一致。

**④ 前端接入路径（site 已实现，2026-09-09）**：device 接口仅内网可达 → site 网关转发端点
`GET /data-statistics/video-collect`（DeviceStatsClient：device 响应为 `{success,code,desc,data}`，与 mq 的 `{code,msg,data}` 结构不同，按 `success` 判定后透传 data 段；device 与 site 共用 APaaS 平台会话，出站自动透传当前登录会话 `X-Session-Id` 头过 device 登录校验，无需管理员角色；device 不可达/业务失败 → site HTTP 502，语义同 4.3）；页面采集表数据 = mq collect-stats 5 行 + video-collect 1 行（前端合并渲染，视频行缺失时自动省略）。

**口径定稿（2026-09-09）**：
1. 应采分母“参与统计视频通道”：定稿为仅接入站点（站点表 epjutj 含 #5#，devicecode 去重），与站点同步口径一致；
   巡检仍对设备树全部通道执行（保持现状），统计只筛接入站点通道；
2. 轮归属：按 round_time（轮实际开始时间）落 30min 窗（窗界整点/半点，与 cron 的 05/35 轮次自然对齐）；
3. video-alert.enabled=false 期间无留痕 → 统计 collected=0、successRate 自然下降（同 mq 断网期语义），
   前端按视频行缺失/全 0 自动省略渲染，避免误读。

## 8. 对接建议

1. **聚合模式**：服务监测页建议"各服务自报指标 + 前端聚合"，mq 只提供自身进程与接收/解析/存储处理量；
   跨服务统一采集 CPU/内存可考虑部署层监控（docker stats / Prometheus），避免各服务实现不一致。
2. **状态阈值归产品**：到报明细的"正常/偏低/异常/未到报"档位由产品定义，mq 提供到报率等原始数字。
3. **查询性能**：msg_info 索引 `(site, tm DESC)`；业务表高频过滤可补 `(site, tm)`。
4. **数据量级**：报文流水 msg_info 全 tag 全量留痕后约 2.6 万行/天（口径以 service-status 接收请求数为准
   =msg_info 当日行数：09-09 22:40 实测 25381 行（当日 msg_info 行数，已含 21:33 进程重启无影响），全天约 2.6~2.7 万；旧格式期每天约 3000 行、且 msg_text 为空无法用于统计），
   业务表每天数百至数千行不等，聚合查询毫秒级，无需离线数仓。
5. **口径一致性**：所有到报/缺测数字统一由 mq 统计接口输出，site/device 不应另起口径（避免大屏数字打架）；
   KPI"站点总数"直接用 arrival-stats 的 stationTotal，不要自行 COUNT 档案表。
