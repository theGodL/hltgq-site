# 天气接入升级方案（免费源版）

> 版本：**v1.2（2026-09-14 评审终审定稿）**
> 项目：hltgq-site（花凉亭灌区数字孪生后端）
> 目标：在**不采购任何商业数据服务**的前提下，用免费源 + 缓存兜底，满足「未来 40 天气象信息、雷达图、台风观测、雨情趋势预判」四项功能需求
> 决策前提：**免费源优先，允许数据获取慢、允许数据延迟，通过 Redis 缓存 + 旧值兜底保证客户始终能看到数据**；本方案不含代码改动
>
> **v1.2 修订说明**：v1.1 针对前两轮评审（A1~A5 / B1~B6 / C1~C5 / E，A6 / B7~B10 / C6~C9）逐条处理后成文，并按评审要求做了**复核实测**（这是本次修订最重要的产出），实测推翻了 v1.0 的两处关键假设——详见 §1.4 与 §2.8。**v1.2 累积独立评审渠道（R1~R9）与评审第三轮（M1/M2 + 补充意见）的修订成果**：新增 §8.4.1 瓦片鉴权方案、`radar.tile.host`、多实例适配方案；修正轮次编号与溯源说明（含**审计链锚定表**）；收窄 P3a 消除依赖倒置；删除顶层瓦片模板。**并经评审第四轮终审通过、可定稿**（终审处理见 §11.7）。全部评审意见处理对照表见 §11。

## 一、需求与结论速览

### 1.1 四项需求

### 1.3 与现有能力的关系

现有 `weather` 包（`/weather/current`、`/weather/hourly`）保持不变，本方案在其之上新增能力，复用已有 Redis 缓存、单飞防击穿、限流、失败降级四大机制。现有逐小时接口上限 16 天（Forecast API 硬上限），继续用于短临场景与模型降雨输入，与本方案新增的日级 40 天接口不冲突。

## 二、免费数据源实测验证（2026-09-14）

### 2.1 验证环境

| 项 | 值 |
|---|---|
| 测试时间 | 2026-09-14 |
| 测试坐标 | `116.359678, 30.378607`（安徽安庆，与生产 `weather.default-location=南排` 同区域） |
| 测试方式 | 开发机直连（PowerShell），只读请求；瓦片做了**内容级验证**（MD5 + 透明像素采样） |
| 结论 | 6 个端点 HTTP 全通，但**其中 2 个数据源存在内容级缺陷**（详见 2.3 / 2.5）——仅验证 HTTP 200 不足，本次补充了数据有效性验证 |

### 2.2 ① Forecast API（1~16 天）✅ 现有能力

```
GET https://api.open-meteo.com/v1/forecast
      ?latitude={lat}&longitude={lon}
      &daily=temperature_2m_max,temperature_2m_min,precipitation_sum,
             precipitation_probability_max,weather_code,
             wind_speed_10m_max,wind_direction_10m_dominant,relative_humidity_2m_mean
      &forecast_days=16&timezone=Asia/Shanghai
```

- 项目已在用同一端点的 `current` / `hourly`，**新增 `daily` 参数即可**，无需新数据源
- `forecast_days` 上限 16（官方硬上限）；含 `precipitation_probability_max`（上游预计算概率）
- 实测：2026-08-29 生产环境已验证；本日复核正常

### 2.3 ② Ensemble API（17~35 天）❌ **实测否决，不采用**

```
GET https://ensemble-api.open-meteo.com/v1/ensemble
      ?models=ecmwf_ifs025&daily=precipitation_sum&forecast_days=35&timezone=Asia/Shanghai
```

**v1.0 假设**：该端点可提供 17~35 天集合预报（官方文档称 Ensemble Mean API 最长 35 天）。
**实测结果**（逐日统计有效成员数，`valid` = 非 null 成员个数）：

| 模型 | 声称跨度 | 实测有效天数 | 边界（首个全 null 日） |
|------|:--:|:--:|------|
| `ecmwf_ifs025`（50 成员） | 35 天 | **15 天** | idx=15 → `2026-09-29`（valid=0） |
| `gfs025`（30 成员） | 35 天 | **10 天** | idx=10 → `2026-09-24`（valid=0） |

> 即：API **接受** `forecast_days=35` 并**返回 35 天的结构**，但**第 16 天（ECMWF）/第 11 天（GFS）起成员值全为 null**——HTTP 200 掩盖了数据缺失。若按 v1.0 方案实现，P0 交付后 17~40 天将整段为空。
>
> 另外：文档提到的「Ensemble Mean」独立端点 `ensemble-api.open-meteo.com/v1/ensemble_mean` 实测 **404**（带不带 `models` 参数均 404）。
>
> **结论**：Ensemble API 不采用。17 天以后改用 EC46（见 2.4）。

### 2.4 ③ Seasonal API（EC46）✅ **改为主力数据源（17~40 天）**

```
GET https://seasonal-api.open-meteo.com/v1/seasonal
      ?models=ecmwf_ec46
      &daily=temperature_2m_max,temperature_2m_min,precipitation_sum,
             cloud_cover_mean,wind_speed_10m_max,
             wind_direction_10m_dominant,relative_humidity_2m_mean
      &forecast_days=46&timezone=Asia/Shanghai
```

**实测结果**：

| 项 | 实测值 |
|---|---|
| HTTP | 200 |
| 有效天数 | **46 天请求中 idx 0~44 有效**（第 45 天），仅最后一天为空 → 覆盖 17~40 天需求**绰绰有余** |
| 模型 | ECMWF **EC46**（次季节延伸预报） |
| 空间分辨率 | 36 km，坐标吸附到网格（`116.25, 30.491802`） |
| 成员数 | 50 个成员（`_member01` ~ `_member50`，另有主字段） |
| 支持变量 | ✅ 全部实测可用：`temperature_2m_max/min`、`precipitation_sum`、**`cloud_cover_mean`**、`wind_speed_10m_max`、`wind_direction_10m_dominant`、`relative_humidity_2m_mean`（7 变量全量响应约 92 KB） |
| 更新频率 | 每日 20:30 UTC |
| 样例值 | `precipitation_sum` 逐日：0.70, 0, 0, 0, …, 13.10, … 0.20, 3.90, 6.30, 11.10, 15.50（数值形态正常，非重复阶梯） |

> EC46 是延伸期集合预报，分辨率粗、只具趋势/概率含义（见 §9.2）。它是**免费源中唯一覆盖 17~40 天的可用数据源**。

### 2.5 ④ RainViewer 雷达 ⚠️ **降级可用（z≤7）**

```
GET https://api.rainviewer.com/public/weather-maps.json     # 帧列表
GET {host}{path}/{size}/{z}/{x}/{y}/{color}/{smooth}_{snow}.png   # 瓦片
```

**帧列表实测**：HTTP 200；`host=https://tilecache.rainviewer.com`；`radar.past` **13 帧**（10 分钟/帧，约 2 小时）；`radar.nowcast` **为空**；`satellite.infrared` 为空。

**官方政策（`rainviewer.com/api/transition-faq.html`，2026 年现状）**：

| 时间 | 变更 |
|------|------|

> 1. **z ≥ 8 返回 200 + 占位图**（不报错），这是极隐蔽的陷阱——前端若不校验会展示"永远无回波"的假图；

### 2.6 ⑤ 中央气象台台风网 NMC ✅

## 三、N1：未来 40 天气象信息

### 3.1 数据分段策略（v1.1 起为两段）

| 段 | 天数 | 数据源 | 精度定位 | 段标记 | 提供字段 |
|:--:|:--:|------|------|:--:|------|
| A | 第 1~16 天 | Forecast API `daily` | 精确预报（上游预计算概率） | `exact` | 温度/降水/概率/天气码/风/湿度 |
| B | 第 17~40 天 | Seasonal API EC46（50 成员聚合） | **延伸期趋势**（36 km） | `extended` | 温度/降水/概率（成员比例）/云量/风 |

> v1.0 的三段（含 17~35 天 Ensemble）因 §2.3 实测缺陷删除；40 天 = A 段 16 天 + B 段 24 天。

### 3.2 接口契约


### 3.3 成员聚合算法（B 段 EC46，50 成员）

对每个日期、每个变量跨成员聚合（**null 成员不计入分母**；有效成员数为 0 时该字段返回 null）：

| 目标字段 | 算法 |
|------|------|
| `tempMax` / `tempMin` | 成员均值 → 四舍五入取整 |
| `rainfall` | 成员降水均值 → **2 位截断** |
| `rainProbability` | `count(成员降水 ≥ weather.rain-trend.min-rain-threshold) / 有效成员数 × 100`，四舍五入（阈值默认 0.1 mm） |
| `humidity` | `relative_humidity_2m_mean` 成员均值 → 取整 |
| `windSpeed` / `windLevel` | `wind_speed_10m_max` 成员均值 → 取整；风级复用现有蒲福换算 |
| `windDirection` | `wind_direction_10m_dominant` 成员均值角度 → 复用现有 16 方位中文映射 |
| `weatherIcon` / `weather` | **三维度映射**（v1.1 补齐云量，采纳评审 B1）：降水概率 ≥ 70% 且雨量 ≥ 25 → 大雨(65)；≥ 70% 且 ≥ 10 → 中雨(63)；≥ 70% → 小雨(61)；≥ 40% → 阵雨(80)；否则按云量：`cloud_cover_mean` < 20% → 晴朗(0)、20~60% → 多云(2)、> 60% → 阴天(3) |
| 有效成员数 | 每日期计算并**记入响应日志**（INFO），供部署后核对样本量（评审 P0 建议） |

### 3.4 拼接、缓存粒度与按需拉取（v1.1 起：评审 A2 + A3）

**规则一：按需拉取（days 决定段数）**

| 请求 days | 拉取段 | 上游调用数 | 说明 |
|:--:|------|:--:|------|
| ≤ 16 | 仅 A（Forecast） | 1 | B 段纯属浪费（EC46 响应约 92 KB） |
| 17 ~ 40 | A + B | 2 | 默认场景 |

**规则二：按段缓存、按需拉取、按需截取（v1.1 复审 A6 修订：新鲜度按段独立计时）**

- 缓存 key：`weather:daily:{lon},{lat}`（**不含 days**）
- 缓存值结构（**每段各记 `expireAt`，无顶层过期时钟**）：

```json
{
  "updatedAt": "2026-09-14T15:00:00",
  "segments": {
    "exact":    { "pulledAt": "...", "expireAt": 1789512000000, "list": [ ... 16 天 ... ] },
    "extended": { "pulledAt": "...", "expireAt": 1789512000000, "list": [ ... 24 天 ... ] }
  }
}
```

- **为什么按段算 `expireAt`（复审 A6）**：顶层单一 `expireAt` 有两个坏结果——① 补 B 段后若沿用顶层时钟，B 段刚拉的新数据会随 A 段的旧时钟提前过期（无谓刷新）；② 若补段时重置顶层时钟，A 段被"续命"（最多 +3 h），语义混乱。故 **`expireAt = 该段 pulledAt + TTL`，判定与写回只在段内进行**。
- 读取流程（**段级判定，不再整体判定**）：

| 场景（`need` = days ≤ 16 → `{exact}`；否则 `{exact, extended}`） | 行为 |
|------|------|
| `need` 各段齐备且各自 fresh | 合并 → 按 `date` 去重（`exact` 优先）→ 升序 → **截取前 `days` 天**返回 |
| `need` 各段齐备、但存在 stale 段 | **立即返回**（新+旧混合，可接受）+ **仅对 stale 段**后台异步刷新（去重） |
| `need` 存在缺失段（从未拉过，**或旧值已超 24 h 上限**） | **按 miss 处理：同步补拉缺失段**（≤ 3 s）；已有 stale 段同时走异步刷新。补拉成功 → 合并返回；**补拉失败 → 返回已有段 + `degradedSegments` 标记**（不静默、不丢弃） |
| 所有需段均不可得 | `source=default` + 空 list（降级占位） |

- 写回：**只更新本次所拉段的 `pulledAt` / `expireAt`**，其余段原样保留（互不干扰）；Redis key 级 TTL = `max(各段 expireAt) + 旧值上限(24 h)`，避免某段先被淘汰。
- 这样 `days=7` 与 `days=40` 交替请求不会互相污染，各自只拉必需段，且**补段不会缩短已有段的寿命**。

**规则三：日期对齐（不用数组下标拼接）**

1. 以 `date`（`yyyy-MM-dd`，`Asia/Shanghai`）为主键对齐（两段起始日可能因时区/更新时刻漂移 1 天）
2. 优先级 `exact` > `extended`；同日期重复时保留 `exact`
3. 只保留今天（含）之后；缺失日期不补行（不伪造数据）
4. 某段整体失败：跳过该段、保留其余段并打 WARN（不抛 5xx）；**同时置 `degradedSegments`**（B 段失败 → `["extended"]`），`days` 如实反映实际天数（16）——即"部分数据 + 显式标记"，既不静默也不丢弃有效段（复审 A6 细化）

### 3.5 缓存、并行与超时（v1.1 起：评审 A4）

| 项 | 值 | 说明 |
|------|------|------|
| 缓存 TTL（新鲜期） | **每段独立** 3 小时（+30 分钟抖动，`expireAt = pulledAt + TTL`） | EC46 每日更新一次、回退保守；按段计时见 §3.4 规则二 |
| 旧值上限 | 24 小时 | 见 §7.1 |

| 单飞 | 复用现有机制（同 key 并发仅一次上游） | 含补段场景 |
| 限流 | 复用（10 QPS），命中缓存不走上游 | |

| 字段 | 说明 |
|------|------|
| frames[].time / timestamp | 帧时间（北京时间）/ epoch 秒 |
| frames[].path | 帧标识（= 上游 path）；**后端据此拼接上游 URL，前端无需理解其结构** |
| **frames[].tileUrlTemplate** | **唯一用法（复审 R4；v1.2 已删去顶层模板）**：该帧的完整瓦片模板，`frame` 已替换为实际 path——前端只处理 `{z}/{x}/{y}`，**无需自行拼接、也无 URL 编码问题** |
| frames[].type | 实测仅 `past`（`nowcast` 官方已停；若上游恢复自动带出） |

| color | 固定 4（上游仅保留 Universal Blue） |
| ~~tileUrlTemplate（顶层）~~ | **v1.2 已删除**（评审第三轮意见：双模板并存会给前端选错的机会，而顶层模板仍需自行替换 `{path}`，正是 R4 要消灭的易错点）。另注：查询参数中的原始 `/` 本为合法（RFC 3986 的 query 允许 `/`，非语法错误），**保留原始 `/` 即可、无需 `encodeURIComponent`** |
| ~~host~~ | **不返回**：瓦片上游 host 由后端固定配置 `radar.tile.host` 提供（复审 R2），**不从上游响应动态取**（防 SSRF） |

**② 瓦片代理**

```
GET /weather/radar/tile/{z}/{x}/{y}?frame={path}
```

| 项 | 规则 |
|------|------|
| 参数校验 | `z`：**0 ≤ z ≤ 7**，越界 400（**主动拦截 z≥8，避免后端把占位图透传给前端**）。**不设 z 下限业务限制（复审 B10）**：z 越小视野越大、单屏瓦片数越少，不产生额外成本，下限交前端按交互设计决定 |
| 鉴权（复审 R1） | 由现有 `AuthInterceptor` 拦截（`auth.enabled=true`）——**瓦片加载方式决定鉴权方案，详见 §8.4**：默认靠同源 `sessionId` Cookie 自动携带；若跨源/纯 Header 调用则需白名单 + 终端限流 |
| `frame` 校验（评审 B4 + 复审 B9） | 必须满足 `^/v2/radar/[0-9a-fA-F]{8,16}$`（**用 `Matcher.matches()` 全匹配**），且长度 ≤ 32；不满足 400（防 SSRF）。长度检查与正则范围**确有重叠**（前缀 11 + 8~16 = 最多 27 字符），但**予以保留**：它是正则匹配前的**廉价短路**，用于挡住超长输入、避免其进入正则匹配路径（评审第三轮意见"可留可删"，此处选择保留并说明理由）。**已删除原 `^\d{10}$` 纯数字分支**（复审 B9）：时间戳式路径（如 `/v2/radar/1603125600`）**本身就是全数字、天然命中 `[0-9a-f]`**，独立分支冗余；同时修掉 `|` 破坏 Markdown 单元格的问题；`frame` 只接受 `frames[].path`，传 `timestamp` 会 400 |
| 上游 URL（复审 R2） | `{radar.tile.host}{path}/256/{z}/{x}/{y}/4/1_1.png`（size/color 固定，不接受客户端自定义）。**host 取自配置项 `radar.tile.host`，固定为 `https://tilecache.rainviewer.com`，绝不从上游响应动态取**（否则 path/host 双外部输入 → SSRF）；启动与帧刷新时把上游报告的 host 打 INFO 日志，便于发现漂移 |
| 上游失败 | 404（前端该瓦片空白，不阻塞其余） |

### 4.3 缓存设计

| 数据 | 位置 | key | TTL | 说明 |
|------|------|------|:--:|------|
| 帧列表 | Redis | `weather:radar:frames` | 5 分钟（+1 分钟抖动） | 上游 10 分钟/帧 |
| 瓦片 | **进程内 LRU** | `{path}_{z}_{x}_{y}` | 30 分钟 | 帧 path 不可变；不入 Redis（二进制 + 高基数） |

- LRU：`LinkedHashMap(accessOrder=true)` 同步包装，容量 `radar.tile.cache-max-entries`（默认 3000，约 10~15 MB）
- **z≤7 下相同视野的瓦片总数有限**（灌区场景常看 z=6~7，几个缩放级 × 数个帧 ≈ 数百张），LRU 命中率预期较高——这是应对上游 100/min 限流的关键
- **瓦片预热（复审 B8，可选）**：瓦片 key 含帧 `path`，而**帧每 10 分钟滚动一次**——**启动时一次性预热在下一帧即失效**。若做预热，必须挂在「帧列表刷新任务」之后，且只预热**当前最新帧**的默认视野（见 §7.4）

### 4.4 上游限流与并发控制（v1.1 起：评审 B2）

**为什么要单独设计**：RainViewer 限流是 **100 请求/IP/分钟，按我方服务器出口 IP 计**（非终端用户 IP）；地图拖动/缩放会瞬时产生数十个瓦片请求，且 RainViewer 的限流按请求数（**含缓存未命中才计数**——后端命中 LRU 时不请求上游，不计数）。

| 机制 | 设计 |
|------|------|
| **上游令牌桶** | 独立限流器：`radar.upstream.limit-per-minute=90`（**留 10% 余量**），超出则**直接返回 404 占位**（不排队、不重试），前端保留上一帧/空白 |
| **并发信号量** | `Semaphore(8)`：限制同时发往上游的瓦片请求数，避免瞬时打满连接与线程 |
| **强缓存优先** | 请求先查 LRU；命中直接返回（不消耗上游配额） |
| **终端维度限流（复审 R8，默认开启）** | 按客户端 IP 的固定窗口限流：`radar.client.limit-per-minute=600`（**宽松阈值**：一次拖动约 20~40 张，正常用户远达不到；作用是防单用户刷爆 LRU 与上游配额）。**若瓦片接口走白名单/匿名访问，此项为必需品**；即便走同源 Cookie 鉴权也建议保留（防内部滥用） |

> **关于复用现有全局限流**（评审指出的问题）：现有 `WeatherService.checkRateLimit()` 是**全局单窗口 10 QPS、阈值不可参数化**（代码确认），无法直接给瓦片接口使用，也不能简单"复用"。
> **处理方式**：抽出 `weather/support/RateLimiter.java`（固定窗口，构造时传入阈值），现有接口改用 `RateLimiter(10)` 实例，**对外行为完全不变**；瓦片接口使用独立的分钟级令牌桶。这样 8.3 的配置项才有落点。

### 4.5 前端接入要点

1. 底图之上叠加 XYZ 图层，`maxZoom` 取接口返回的 `maxZoom`（=7），**禁止请求 z≥8**
2. 时间轴按 `frames` 升序播放，间隔约 500 ms，末帧停住
3. 帧时间标签用 `frames[].time`
4. **数据来源署名（合规要求，复审 B7）**：雷达图注标 `Radar by RainViewer`；**Open-Meteo 数据按 CC-BY 4.0 许可、强制署名**，需标 `Weather data by Open-Meteo.com (CC-BY 4.0)`（建议带链接）。⚠️ **该署名义务与雷达无关、对现有 `/weather/current`、`/weather/hourly` 同样成立**（它们已在用 Open-Meteo），建议前端在天气模块统一放一次（图注或关于页），不要只加在雷达图上
5. **明确告知：只能回放过去约 2 小时，无未来外推**
6. **鉴权与同源（复审 R1，交付前必须确认）**：瓦片由浏览器 `<img>`/XYZ 图层直接加载，**无法携带自定义 Header**。本项目鉴权支持 `sessionId` Cookie（`SessionContextService` 三级提取：`X-Session-Id` → `Authorization` → Cookie `sessionId`）——**若同源则浏览器自动带 Cookie、零改造可行（条件结论，以 §10.3-1 确认为准，非单方面结论）**。三个必须遵守的前提：① 页面与瓦片 API **同 scheme + host**（**端口不影响 Cookie 携带**；跨站则 `SameSite=Lax` 下图片子请求不带 Cookie → 401）；② **登录 Cookie 的 `Path` 属性须覆盖 `/weather/radar/tile`**（Cookie 的 path 匹配是真实的携带前提）、`Secure` 属性须与页面协议匹配（https 页面请求 http 瓦片会被拦）；③ **不要给图层设 `crossOrigin`**——设了会切成 CORS 模式、不带 Cookie → 401。若前端为纯 Header 调用（无 Cookie）或跨源，按 §8.4 备选方案处理
7. 瓦片 URL 直接用 `frames[].tileUrlTemplate`（已含 frame），只让地图引擎替换 `{z}/{x}/{y}`；**未登录时瓦片返回 401 JSON**（拦截器对图片请求不跳转、直返 401），表现为图层整体加载失败而非静默空白，可用于自查鉴权

### 4.6 降级策略

| 场景 | 行为 |
|------|------|
| 帧列表上游失败 | 返回上次缓存（stale，上限 1 小时）；无缓存 → `frames: []`，前端不叠图层 |
| 瓦片命中 LRU | 毫秒返回（不消耗上游配额） |
| 上游限流/超时/失败 | 404，前端空白（不影响底图与其他瓦片） |
| 上游有回波但为占位图 | 后端已在 z 校验层拦截（z ≥ 8 直接 400），不会透传占位内容 |

### 6.4 不落独立缓存（v1.1 起：评审 A1）

**v1.0 的问题（评审指出，正确）**：§6.5 说「与 daily 共用日级缓存」，§7.2 却给了独立的 `weather:rain-trend:*` key 与 1h TTL——**两者矛盾**，且独立缓存会在 daily 刷新后继续用旧数据计算，形成不一致窗口。

> 补充说明：评审给出的理由是「1h TTL 比 daily 的 3h 更短、更陈旧」——**这一点表述需要修正**：TTL 更短意味着刷新更频繁，本身不会更陈旧；真正的缺陷是「独立缓存造成的不一致窗口 + 冗余存储」。

**修订后设计**：

1. `/weather/rain-trend` **不写 Redis**，每次请求读取 `weather:daily:{lon},{lat}` 的缓存结构（含 §7.1 的 stale 判定），**实时计算**概览字段
2. O(40) 的遍历 + 求和计算成本可忽略（微秒级），且与 `/weather/daily` **永远一致**（同一份数据源）
3. 缓存矩阵（§7.2）删除 `weather:rain-trend:*` 行；配置项仅保留 `weather.rain-trend.min-rain-threshold`（概率阈值），删除 `weather.rain-trend.cache-ttl-minutes`
4. 依赖关系：rain-trend 的可用性完全继承 daily（daily 降级 → rain-trend 同降级，返回 `source: default` + 空 list）

### 6.5 为什么不做单接口聚合（实测 + 分层理由）

1. `weather` 包定位为「外部气象数据代理」，不查业务库（保持分层，评审 D 项亦认可）
2. 实测段已有成熟接口（灌区/水库雨情），前端组合成本极低
3. 如甲方坚持单接口：新增**业务侧**聚合接口（controller 层调用 `weather` + 雨量 service），而非让 `weather` 反向依赖业务库

## 七、缓存与性能设计（统一）

### 7.1 stale-while-revalidate + 线程模型（v1.1 起：评审 A5）

**策略**（沿用 v1.0，评审已认可）：

```
读缓存（多段结构：daily）
 ├─ 需段均 fresh（now < 各段 expireAt）      → 直接返回（合并 + 截取）
 ├─ 需段齐备但有 stale 段                    → 立即返回旧值（新+旧混合）+ 仅对 stale 段后台异步刷新
 ├─ 存在缺失段（未拉过 / 旧值超 24 h）       → 同步补拉缺失段；成功→合并返回，失败→返回已有段 + degradedSegments
 └─ 无任何可用段                              → 同步加载；失败 → 降级占位

读缓存（单值结构：typhoon / radar frames）
 ├─ fresh（now < expireAt） → 直接返回
 ├─ stale（已过期）         → 立即返回旧值 + 后台异步刷新（去重，不阻塞）
 └─ miss（不存在）          → 同步加载；失败 → 降级占位
```

**线程模型约束（评审 A5，必须遵守）**：

| 约束 | 说明 |
|------|------|
| **独立命名线程池** | 后台刷新使用 `weather-refresh`（核心 2 / 最大 4 / 队列 64 / 命名线程工厂），**严禁使用 `ForkJoinPool.commonPool`**（`CompletableFuture.supplyAsync` 默认池）——境外慢源会阻塞全进程并行流 |
| **两套模式共存** | ① **同步模式**（miss）：请求线程等待 `pendingRequests` 结果，超时 3 s 降级；② **异步模式**（stale）：请求线程立即返回旧值，刷新任务在线程池中执行 |
| **刷新去重与互斥** | 两种模式共用同一 `pendingRequests` 去重：同 key 已有刷新在跑则不再提交；**异步刷新不占用同步等待窗口**（等待方只在 miss 时等待，stale 场景不等待） |
| **失败清理** | 无论成功/失败，`finally` 中移除 pending 标记，避免"卡死的刷新"永久阻塞后续刷新 |
| **旧值上限** | 旧值最长可用 24 h；雷达帧列表 1 h、台风 6 h、日级 24 h。**日级按段计算**：某段超限即视为**该段缺失**，走同步补拉（而非"返回旧值"），避免展示过期数据造成误解 |
| **段级新鲜度（复审 A6）** | 日级缓存的 fresh / stale / miss **按段判定**（`exact` / `extended` 各有 `expireAt`）：需段齐备但有 stale 段 → 立即返回（新+旧混合值）；**"立即返回旧值"不适用于缺失段**——缺段必须同步补拉，否则会返回不满足请求 `days` 的结果 |
| **部分数据必须显式标记（复审 A6 细化）** | 补拉失败时既不静默、也不丢弃已有段：返回已有段 + `degradedSegments`（如 `["extended"]`）+ `days` 如实反映实际天数 |
| **缓存结构** | 单值接口：`{ "expireAt": …, "data": … }`，Redis TTL = `expireAt + 旧值上限`；**日级为多段结构**（每段各记 `expireAt`，见 §3.4 规则二），key 级 TTL = `max(各段 expireAt) + 旧值上限` |
| **适用范围** | 仅新接口（`daily` / `typhoon` / `radar frames`）；现有 `current`/`hourly` 行为**不变**（避免回归） |

### 7.2 缓存 key 与 TTL 矩阵（v1.1 起）

| 数据 | key | TTL（新鲜期） | 旧值上限 | 上游更新 |
|------|------|:--:|:--:|:--:|
| 实时卡片（现有） | `weather:now:{lon},{lat}` | 10~13 min | — | 15 min |
| 逐小时（现有） | `weather:hourly:{lon},{lat}` | 10~13 min | — | 1~6 h |
| **40 天日级（新）** | `weather:daily:{lon},{lat}` | **每段独立** 3 h（+30 min 抖动） | 24 h（**按段**） | 6~24 h |
| **雷达帧列表（新）** | `weather:radar:frames` | 5 min（+1 min 抖动） | 1 h | 10 min |
| **雷达瓦片（新）** | 进程内 LRU：`{path}_{z}_{x}_{y}` | 30 min | — | 帧不可变 |
| **台风列表（新）** | `weather:typhoon:active` | 30 min（+10 min 抖动） | 6 h | 3~6 h |
| **台风详情（新）** | `weather:typhoon:detail:{id}` | 30 min（+10 min 抖动） | 6 h | 3~6 h |
| ~~雨情趋势~~ | ~~`weather:rain-trend:*`~~ | **已删除**（评审 A1）：由 `/weather/rain-trend` 实时读 daily 缓存计算 | — | — |

- 坐标统一 6 位小数归一（`String.format(Locale.US, "%.6f,%.6f", lon, lat)`）
- 台风 key 不含坐标（全国范围数据）
- **日级 TTL 按段独立计时**（`exact` / `extended` 各记 `expireAt`），key 级 TTL = `max(各段 expireAt) + 24 h`；补段只刷新所拉段（复审 A6，详见 §3.4 规则二）

### 7.3 限流与并发控制（v1.1 起：评审 B2）

| 接口 | 机制 | 说明 |
|------|------|------|
| 现有 `current` / `hourly` | 全局固定窗口 10 QPS | **行为不变**（重构为 `RateLimiter(10)` 实例，等价） |
| `/weather/daily`、`/weather/rain-trend`、`/weather/typhoon/*` | 同一 `RateLimiter(10)` | 命中缓存不消耗上游 |
| `/weather/radar/tile/*` | **不进全局限流**；改用「上游令牌桶 90/min + 并发信号量 8」 | 地图拖动会瞬时数十请求，全局限流会误伤；真正的约束在上游 100/min |

**改造点（评审指出的关键问题）**：现有 `checkRateLimit()` **阈值硬编码在 `WeatherService` 内、不可参数化**，因此 v1.0 的 `radar.rate-limit.qps` 配置**无处落地**。修订为抽出 `weather/support/RateLimiter.java`（构造传入阈值与窗口长度），现有接口注入 `RateLimiter(10)`，对外行为零变化。

### 7.4 预热任务（v1.1 起：评审 C4 / C5）

项目已启用 `@EnableScheduling`（`HltgqApplication`），新增 `weather/task/WeatherWarmupTask`：

| 项 | 设计 |
|------|------|
| 日级预报 | 每 3 小时刷新（错开 EC46 的 20:30 UTC 更新）：`0 30 1,4,7,10,13,16,19,22 * * ?`<br>⚠️ **Spring cron 为 6 位（秒 分 时 日 月 周）**，`?` 自 Spring 5.3 起支持；**不要按 Quartz 7 位格式（含年）照搬** |
| **时区前提（复审 R7）** | cron 按 **JVM 默认时区**触发。已核实 `Dockerfile` 设 `ENV TZ=Asia/Shanghai` 并将 `/etc/localtime` 软链到上海时区，Java 8 在 Linux 下取 `/etc/localtime` → **默认时区即 Asia/Shanghai，上述表达式无需调整**（01:30 / 04:30 / … 均为北京时间）。**若现场改用 docker-compose 覆盖 TZ、或宿主为 UTC，需同步换算**：EC46 每日 20:30 UTC 更新 = 北京 04:30，故首轮刷新排在 04:30 之后 |
| 雷达帧列表 | 每 5 分钟刷新（**不预热瓦片**，瓦片按需加载并进 LRU） |
| 雷达瓦片（可选，复审 B8） | **必须挂在帧列表刷新之后**：帧每 10 分钟滚动，瓦片 key 含帧 `path`，**启动时一次性预热在下一帧即失效**；预热内容 = **当前最新帧**的默认视野（自 `radar.prewarm.center-zoom` 起算，约 20~40 张，占 90/min 令牌桶约 4%）。默认关闭 |
| 台风 | 每 30 分钟**拉取列表**（列表本身必须拉才知道是否有活跃台风）；**仅当存在 `start` 项时才拉详情**——即"跳过的是详情拉取，不是列表拉取"（评审 C5 表述修正） |
| 预热坐标（复审 C8） | **默认取 `weather.site-lon/lat`（单一来源，避免坐标两处维护）**；`weather.warmup.locations` 留空即用默认值，**仅需多站点预热时才填写**（多组逗号分隔） |
| 开关 | `weather.warmup.enabled`，默认 `false`，部署后按需开启 |
| 失败处理 | 仅打日志，不影响请求链路；仅在该 key 已 stale/miss 时执行（避免无谓调用） |

#### 8.4.1 雷达瓦片接口鉴权方案（代码实证）

**鉴权链路（读 `WebMvcConfig` / `AuthInterceptor` / `SessionContextService` 确认）**：

| 项 | 实现事实 |
|------|------|
| 开关与范围 | `auth.enabled=true`（**当前已开启**），拦截 `/**`，仅 `excludePathPatterns("/error")` |
| 会话提取（三级） | ① `X-Session-Id` 头 → ② `Authorization` 头（兼容 `Bearer ` 前缀）→ ③ **Cookie `sessionId`** |
| 白名单 | 配置项 `auth.white-list`（**前缀匹配**，当前值 `/archive/sync/trigger`）+ 代码固定 `/auth/login`、`/error` |
| 未登录行为 | `Accept` 含 `text/html` → 302 跳平台登录页；**否则返回 401 JSON**。图片请求的 `Accept` 为 `image/*`（不含 `text/html`）→ **瓦片拿到 401 JSON，表现为图层加载失败** |
| 既有先例 | 15 个静态页面（`*.html`）走同一拦截器，**靠登录后的 Cookie 放行**（`WebMvcConfig` 注释已明确） |

| 方案 | 适用前提 | 做法 | 评价 |
|:--:|------|------|------|
| **① 同源 + Cookie（默认推荐）** | 瓦片 URL 与页面**同 scheme + host**（**端口不影响 Cookie 携带**；跨站时 `SameSite=Lax` 下图片子请求不带 Cookie） | **零改造**：浏览器对 `<img>` 自动带 `sessionId` Cookie；已登录页面天然通过。**交付前须核对 Cookie 属性**：`Path` 覆盖 `/weather/radar/tile`、`Secure` 与页面协议匹配。**禁止给图层设 `crossOrigin`**（会切成 CORS 模式、不带 Cookie → 401） | ✅ 与现有页面机制完全一致（同一 Cookie 通道）；安全性最好 |
| ② 白名单 + 终端限流 | 前端为**纯 Header 调用**（无 Cookie）或瓦片**跨源** | `auth.white-list` 追加 `/weather/radar/tile`（前缀匹配）；**必须同时开启** `radar.client.limit-per-minute` 与上游令牌桶 | ⚠️ 匿名可拉取，但**风险已收敛**：瓦片内容为**公开气象数据**（非业务敏感数据），且仍受 **z ≤ 7 上限**与**上游令牌桶 90/min** 双重约束，无法被用于放大攻击或批量数据爬取（评审第三轮意见：此处定性说明备安全审计用）。**仍需业务/安全确认** |
| ③ 短时签名 token | ① ② 均不可行 | 帧列表额外返回 `sig`（HMAC of path + exp），瓦片校验 `sig`/`exp` | 成本最高；仅当前端完全无法用 Cookie 时采用 |
| ❌ 排除项 | — | 不给瓦片加 `@RequireAdmin`；不指望 302 跳转（图片请求会把登录页 HTML 当图片解析）；不假设"仅内网访问"（运维拓扑未定） | — |

> **结论**：**方案 ① 为既定默认**（只需确认"瓦片 URL 与页面同 scheme + host、且 Cookie 属性覆盖瓦片路径"这一件事，已列入 §10.3 第 1 项）；仅当确认为**跨源/纯 Header** 时才落地 ②，并同步开启终端限流。
>
> **该结论的边界（v1.2 补，回应评审 M1）**：「同源场景零改造可行」是**条件结论**——本项目鉴权链路存在 Cookie 通道这一点由代码实证，但"是否同源、Cookie 是否覆盖瓦片路径"取决于前端与网关部署形态，**须由 §10.3-1 的前端/运维确认项回答，不由方案方单方面宣布**。

### 9.4 对客户的口径建议

> 天气数据来自公开免费气象源（Open-Meteo / 中央气象台台风网 / RainViewer）：16 天内为常规预报，17~40 天为**延伸期趋势参考**（36 km 分辨率，不可用于调度决策）；雷达为**过去约 2 小时的流域尺度回放**（可看雨带方位与移动，不提供局地细节与未来外推）。系统通过缓存保证展示可用，上游异常时展示最近一次成功数据。

> **数据来源署名（复审 B7，必须在前端体现）**：`Weather data by Open-Meteo.com (CC-BY 4.0)`、`Radar by RainViewer`、台风数据来源「中央气象台台风网」（后者为披露习惯，非强制）。**注意：Open-Meteo 署名义务对现有实时/逐小时接口同样适用**，不是本次新增才有。

**多实例适配方案（复审 R6，仅当第 2 项确认为多实例时执行）**

|------|------|------|:--:|

| 日级 / 台风 / 帧列表缓存 | Redis | 天然共享，无需改动 | 无需 |

### 11.2 v1.0 评审：需要修正的评审判断（3 处）

| 评审项 | 评审原判断 | 修正说明 |
|:--:|------|------|
| A1 理由 | 「1h TTL 比 daily 的 3h 更短、更陈旧」 | **TTL 更短意味着刷新更频繁，不会更陈旧**。真实缺陷是「独立缓存造成不一致窗口 + 冗余存储」。结论（不落独立缓存）正确并已采纳，理由已按实际机制重述 |
| B2 方向 | 建议「按 IP/会话维度限流或改滑动窗口」 | 方向对但**未命中主要矛盾**：RainViewer 的 100/min 限流按**我方服务器出口 IP**计，终端用户 IP 限流解决不了该约束。故主力机制改为「上游令牌桶 + 并发信号量」（终端维度限流列为可选增强）。此外固定窗口"双倍突刺"在只读缓存场景影响有限，本次一并重构为可参数化实现 |
| B3 归因 | 推测 nowcast 为空「更可能是中国区域无 nowcast 覆盖而非服务停更」 | **归因不成立**：RainViewer 官方 transition FAQ 明确 **2026-01-01 起 nowcast 全球停止**，且免费层仅保留 past 数据；`weather-maps.json` 本身是全局接口（不按区域过滤），不存在"区域无覆盖"情形。**验证建议本身非常有价值**——执行内容级验证后发现更严重的问题：**z≥8 全部返回统一占位图** |

### 11.3 v1.0 评审未覆盖、实测发现的方案级缺陷（2 处，会直接导致交付失败）

| # | 缺陷 | 发现方式 | 修正 |
|:--:|------|------|------|
| 1 | **Open-Meteo 集合预报免费层远期无数据**：`ecmwf_ifs025` 仅 15 天、`gfs025` 仅 10 天有效，之后整列为 null（API 仍返回 35 天结构，HTTP 200） | 按评审 P0 建议「抽查第 30~35 天成员 null 比例」执行 → 发现不是"比例偏低"而是"整列为空" | N1 改为**两段**（1~16 天 Forecast + 17~40 天 EC46）；Ensemble client 从改造清单删除 |
