## 1. 逐接口变更对照

### 1.1 `/decision` 配水调度（手册 4.7）—— **P0，破坏性**

| 项 | 我方现状（基线） | 新手册（20261121） | 差异判定 |
|----|------------------|--------------------|----------|
| `供水分配汇总` | **18 行逐旬数组**（2026-10-27 实测），逐行落库 `decision_supply_alloc`，详情以 `supplyAlloc` 返回，前端渲染 18 行逐旬表 | **object**：`{需水量, 建议供水量, 塘坝补水量, 补水后总供水量, 净需水量合计, 是否满足}`，且手册注明「与 `总计_全部旬` **同口径同值**，仅按 Excel sheet 名别名提供」 | **破坏性** |
| `总计_全部旬` | object 年度合计，入 4 张扩展表 | object 年度合计（语义不变） | 一致 |
| `支渠明细` | object `{旬标签: [行...]}`，逐行展开落库 | object（同结构） | 一致 |
| `缩放系数` | object `{旬标签: 系数}` | object | 一致 |
| `年汇总` | 未采集 | object 年度合计（含 `是否满足`） | 新增，可选 |
| `口径变更` | 未采集 | array<string>，V3 与 V2 口径差异说明 | 新增，可选 |
| `月汇总_5至10月` / `分灌区汇总` / `片区汇总` / `行政区月汇总` / `行政区年汇总` | 已解析落库 | 同 | 一致 |
| 上游依赖 | 需水结果文件须含 `行政区`、静态表 `支渠限制流量.xlsx`/`面积分配.xlsx` | 同 | 一致 |

**后端影响（`DecisionService#execute` 第 4 步，L278-292）**

```java
// 现状：按数组迭代逐行落库
for (JsonNode item : response.path("供水分配汇总")) { ... }
```

Jackson 的 `ObjectNode` 迭代结果是**各键的值**，若模型真返回 object，会把「需水量/建议供水量/…」这些标量当成 18 条「旬行」，落库得到 `tenday_label = null` 的脏行，同时真正需要的逐旬数据一条都不会有。

**处理方案（二选一，需模型方先答复第 4 章问题 1）**

- **方案 A（优先争取）**：请模型方**保留 18 行逐旬数组**（或新增独立字段如 `供水分配汇总_逐旬`）。后端现有逻辑零改动，前端零改动。
- **方案 B（模型方确定只给 object 时的后端兜底）**：后端按 `支渠明细` 按旬聚合自算逐旬表，字段映射如下；并且仍把 object 形态归档进 4 张扩展表供「全旬合计」展示。

| 逐旬字段（落库列） | 取值规则（按旬聚合 `支渠明细`） |
|--------------------|-----------------------------------|
| `tenday_label` / `sort_order` | 旬标签 + 旬序 |
| `demand_volume` | Σ 该旬各支渠「需水量」 |
| `suggested_supply` | Σ「建议供水量」 |
| `pond_supplement` | Σ「塘坝补水量」 |
| `supply_after_pond` | Σ「补水后总供水量」 |
| `is_satisfied` | 模型 `总计_全部旬.是否满足` 的旬级语义取支渠明细「是否满足」（若全部 `#1#` 则 `#1#`） |
| `net_demand` | 保持 null（仅 `总计_全部旬.净需水量合计` 有值，与旧口径一致） |

一致性校验：聚合合计与 `总计_全部旬` 的需水量/建议供水量/塘坝补水量比对，差异 > 0.01 时打 `log.warn`（联调项日志化，不阻断）。
**落库表结构与详情接口字段不变**（`decision_supply_alloc` / `supplyAlloc`），前端 18 行表照常渲染 → **前端零改动**，仅口径说明需注明「逐旬合计口径与模型年度合计一致」。

工作量：方案 A = 0；方案 B ≈ 60 行（`DecisionService` 一个聚合方法 + 校验日志），无 DDL 变更。

| 响应 `summary` | 解析 `总来水量_万方`、`最高水位_m`、`入库洪峰流量_m3s`（另有明细回退） | 8 个键：起调水位_m/入库洪峰流量_m3s/入库洪峰出现时刻/最高水位_m/最高水位出现时刻/总来水量_万方/最低水位_m/最大下泄流量_m3s | 一致，`最低水位_m`/`最大下泄流量_m3s` 可增量使用 |

**模型方答复（2026-11-23，问题 3）**：① 是，发电流量固定 **30 m³/s/台**；启用发电时 1~4 台对应 30/60/90/120，关闭发电为 0（总下泄还需叠加隧洞与溢洪道）；② **显式传入的 false 生效**，默认值仅在字段省略时使用；按业主「三开关默认全关」口径把三个开关都传 **JSON 布尔值 false**，三个分项与合计下泄均为 0——**不要传字符串 "false"**；③ 历史方案只要在复算时**回传已保存的 start_level** 就不受默认值调整影响（回传 80 仍按 80 起调）；旧方案若依赖原默认值且复算时不传该字段，会按 70 起调；这只是起调水位不变，要完整复现旧版结果还需核对模型版本、发电规则与设施开关。

**后端处理（✅ 已实施）**：`ShortForecastRequest` 增加可选 `powerUnits`（1~4），`ShortForecastService#submit` 校验后组装 `power_units` 透传（省略按 1 台）；三开关仍按 `Boolean` 序列化为 JSON 布尔值（`ModelClient` 用 ObjectMapper 写 JSON，不会产生字符串）；`loadLatestLevel` 两处日志与 javadoc 的默认值文案 80.0→70.0。不落库（提交值归档在 `record.request_json`，需回看时从中解析）。
**前端配合**：如业主需要按机组数调度，页面增加「机组台数」下拉（1~4 台，对应发电流量 30/60/90/120 m³/s）与「起调水位默认 70 m」文案；不需要则零改动（后端默认 1 台 = 30 m³/s）。
**历史方案复算**：平台当前无复算入口，不涉及改动；如后续新增复算，必须从 record 回传 `start_level` 与三开关。

### 1.4 `/forecast/custom` 短期来水·自定义出库（手册 4.2.1）—— **P1 新接口，待业主定**

- 与常规版共用 `start`/`end`/`rainfall`/`start_level`，新增**必填** `q_out`（逐小时总出库流量，与 `rainfall` 等长）；不接受设施开关与机组台数。
- 响应 `data` 字段不同：`时间`/`降雨量_mm`/`入库流量_m3s`/`水位_m`/`库容_万方`/`出库流量_m3s`；`curve` 仅含水位与库容。
**模型方答复（2026-11-23，问题 4）**：若业主要按给定的逐小时总出库流量推演水位与库容，就开放 `POST /forecast/custom`，**暂定提供**（当前部署代码已提供自定义路由）；如只按机组台数与设施开关推演，`/forecast` 已足够。调用时传 `q_out`，**不要同时传设施开关或 power_units**。① `summary` 共 8 键（与常规版同）；其中 **`最大下泄流量_m3s` 是本次输入 q_out 的最大值，不代表水库最大泄流能力**；② `q_out` **没有最大泄流能力上限校验**：每小时一个有限非负值、长度与时点数一致（含首尾），模型直接采用给定值，**不按当时水位对应泄流能力限流**；③ CSV 与 HTTP 逐小时结果同源但格式不同：HTTP 不写 CSV，离线 CSV 对应响应 `data`，均含时间/降雨/入库/水位/库容/出库；HTTP 字段名带单位后缀、浮点保留 4 位，CSV 用简写列名、保留模型输出精度；`curve` 是单独静态对照表（仅库水位_m + 库容_万方），不写入该 CSV。

**后端处理（✅ 已实施）**：新增 `POST /water-forecast/short/custom`（内部调模型 `/forecast/custom`）：
- `ModelClient` 新增 `PATH_FORECAST_CUSTOM`；新增 `ShortForecastCustomRequest`（schemeName/start/end/rainfall/qOut）。
- `qOut` 校验：必填、长度必须等于逐小时步数、每个值非负有限，不合规则 400；**不设泄流能力上限**（不自行编造，与模型口径一致）。
- 起调水位与降雨口径同常规版（自动取坝上最新水位；rainfall 未传自动拉气象），**不传三开关与 power_units**。
- 落库复用短期主表/明细表：三开关恒 `#2#`，`custom_discharge_json` 归档 q_out，`request_json` 归档完整请求；`dailies[].outflow_rate` 取模型 `出库流量_m3s`（常规版取 `合计下泄流量_m3s`），`outflow_volume` 仍按 ×0.36 换算。

**前端配合**：若要使用，需新增「按给定出库过程推演」入口（逐小时出库序列录入/上传，长度随窗口变化）+ 结果展示；若本期不用，后端接口保留、页面无需改动。注意摘要卡不要将 `最大下泄流量_m3s` 标为「水库最大泄流能力」。
