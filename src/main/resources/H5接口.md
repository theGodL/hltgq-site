# H5 移动端接口文档

> 面向 H5 移动端（巡查统计 / 维修养护统计 / 消息中心 / 站点经纬度批量查询 / 巡检计划列表、关联点位与开始巡检 / 巡检问题上报 / 水资源概览 / 人员信息 / 工单处理结果与附件），生产环境路径统一加 `/hltgq-site` 前缀
> 全部接口需登录态（未登录由拦截器统一 302/401 处理）
> 数据来源为低代码平台表（schema `qixiao-apaas`）

---

## 设计说明

1. **消息可见性口径**：告警/举报投诉/意见征集按接收规则（部门/岗位/角色/人员）决定可见范围，只有匹配规则的登录人能看到；某类型未配置规则时全员可见；告警再叠加站点范围（规则未选站点=不限站点，命中多条规则合并范围）。值班提醒与模型计算为「原有定向 + 规则附加接收人」：带班领导与值班人员、方案提交人本人始终收到，消息发送设置中配置的对象额外收到。接收记录由后端在 summary/page 接口被调用时按需同步补建（幂等、不重复），无定时分发；规则收紧/删除时存量接收记录不回滚（已读状态保留）。规则维护入口：管理页面 `message-rule-setting.html`（仅系统管理员）、接口前缀 `/message-rule`，契约见《消息发送设置.md》。
2. **已读口径**：接收记录建立时为未读（`is_read=#1#`），登录人阅读后更新为已读（`#2#`）；列表与未读数均基于当前登录人视角返回。
3. **统计口径**：柱状图巡查数按巡检计划统计（排除草稿 `#1#`、含已取消 `#4#`，按计划开始时间 `start_time` 归月）；维修养护饼图仅统计已提交巡检记录（`status=#2#`）；问题记录全状态、按发现时间 `time` 统计。
4. **图表展示口径（配色、堆叠/并列、轴标题）归前端**，后端只返回权威数据（编码 + 数量 + 完整编码映射表）。
5. **巡检任务可见性口径**：H5 巡检任务列表、点位与开始巡检接口仅对「计划巡检人员」（主表 `"user"`）开放，他人计划不返回、点位与开始接口返回 400；**开始巡检统一走服务端接口**（§5.3，校验归属后落草稿占位记录），不再直连低代码表单新增记录；未开始/进行中按该计划下是否存在巡检记录判定（调用开始接口后即为进行中）。
6. **巡检记录提交幂等**：开始巡检写入的空白占位草稿由列表行 `draftRecordId` 返回，提交时用 `recordId` 更新+提交（§5.3 计算规则 5~6）；后端新增入口（/patrol-record/create、计划页添加巡检记录）也会优先填充空白草稿并清理同计划其余空白草稿，任何客户端都不会产生「草稿 + 正式」两条；空白占位草稿在巡检记录列表与计划「巡检记录」弹窗中不展示。
7. **工单接口与 PC 端共用** `/work-order` 前缀（不在 `/h5` 下，登录态与鉴权方式与其他接口一致）。附件采用「上传即入库、保存时绑定」模式：上传成功即刻返回附件 id（此时未归属任何工单），保存处理结果时用 `attachmentIds` 声明要保留的附件集合；弹窗关闭/取消时必须清理本次新上传且未保存的附件，否则会残留孤儿文件（交互口径见 §8.6）。

## 一、巡查及问题统计（柱状图）

近 12 个月每月巡查任务数（巡检计划口径，含已取消）与问题数量；问题数按风险等级拆分三档，前端按不同颜色绘制（堆叠或并列由前端定夺）。

### 请求

```
GET /h5/patrol-issue-monthly
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:--:|--------|------|
| endMonth | String | 否 | 当前月 | 统计基准月，格式 `yyyy-MM`；返回该月及往前 11 个月（共 12 个） |

### 调用示例

```
/hltgq-site/h5/patrol-issue-monthly
/hltgq-site/h5/patrol-issue-monthly?endMonth=2026-09
```

### 响应

```json
{
  "months": [
    { "month": "2025-10", "patrolCount": 12, "issueCount": 5, "issueLow": 3, "issueMid": 1, "issueHigh": 1 },
    { "month": "2025-11", "patrolCount": 9,  "issueCount": 2, "issueLow": 2, "issueMid": 0, "issueHigh": 0 },
    { "month": "2025-12", "patrolCount": 0,  "issueCount": 0, "issueLow": 0, "issueMid": 0, "issueHigh": 0 }
  ]
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| months | Array | 严格 12 个元素，按月份升序（endMonth 往前 11 个月起），无数据月份补 0，前端 x 轴直接消费 |

**months[].字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| month | String | 月份标签 `yyyy-MM` |
| patrolCount | long | 该月巡查任务数（巡检计划数：排除草稿 `#1#`、含已取消 `#4#`） |
| issueCount | long | 该月问题总数（全状态，含未标注风险等级的记录） |
| issueLow | long | 低风险（`risk_level=#1#`）问题数 |
| issueMid | long | 中风险（`risk_level=#2#`）问题数 |
| issueHigh | long | 高风险（`risk_level=#3#`）问题数 |

### 计算规则

```
1. 基准月 M = endMonth（默认当前月），窗口 = [M−11个月首日, M+1个月首日)（右开区间，避免月末 23:59:59 精度问题）
2. 巡查：t_auto_hltgq_water_patrol_schedule（巡检计划），status IN ('#2#','#3#','#4#')（排除草稿 #1#、含已取消 #4#），按 start_time（计划开始时间）聚合到月
3. 问题：t_auto_hltgq_knc3g_bpzjoh，全状态，按 time（发现时间）聚合到月，
   并按 risk_level 拆 #1#/#2#/#3# 三档
4. 生成 12 个月完整序列，无数据月份补 0
```

### 边界场景

| 场景 | 表现 |
|------|------|
| 某月无任何记录 | 四项计数均为 0 |
| 问题 risk_level 为 null/未知编码 | 计入 issueCount，不计入 issueLow/Mid/High（三档之和可能小于 issueCount） |
| 巡检计划草稿（status=#1#） | 不计入 patrolCount |
| 已取消计划（status=#4#） | 计入 patrolCount（业务口径：取消的计划仍属巡查任务） |

## 二、维修养护统计（饼状图）

已提交巡检记录按巡检结果 `result` 分组计数，固定返回 6 档。

### 请求

```
GET /h5/inspection-result-stats
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:--:|--------|------|
| startTime | String | 否 | 不限 | 巡检时间起（含）`yyyy-MM-dd HH:mm:ss` |
| endTime | String | 否 | 不限 | 巡检时间止（含）`yyyy-MM-dd HH:mm:ss` |

### 调用示例

```
/hltgq-site/h5/inspection-result-stats
/hltgq-site/h5/inspection-result-stats?startTime=2026-01-01+00:00:00&endTime=2026-12-31+23:59:59
```

### 响应

```json
{
  "total": 100,
  "items": [
    { "name": "#1#", "label": "待填写", "value": 2 },
    { "name": "#2#", "label": "正常",   "value": 60 },
    { "name": "#3#", "label": "异常",   "value": 10 },
    { "name": "#4#", "label": "隐患",   "value": 8 },
    { "name": "#5#", "label": "缺陷",   "value": 5 },
    { "name": "#6#", "label": "故障",   "value": 15 }
  ]
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| total | long | 已提交巡检记录总数 |
| items | Array | 固定 6 档（#1#~#6#），无数据的档 value=0 |

**items[].字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| name | String | 巡检结果编码 |
| label | String | 巡检结果名称（后端返回权威映射） |
| value | long | 该结果的巡检记录数 |

### 计算规则

```
1. 巡检：t_auto_hltgq_water_inspection_record，status='#2#'（已提交，排除草稿）
2. 按 result 分组计数：#1# 待填写、#2# 正常、#3# 异常、#4# 隐患、#5# 缺陷、#6# 故障
3. 缺档补 0，固定按编码升序返回
```

## 三、消息中心

消息由五类数据源组成：**告警**（已确认、处理中；接收规则可限定站点范围）、**举报投诉**、**意见征集**、
**值班提醒**（带班领导与值班人员双侧定向 + 规则附加接收人）、**模型计算**（提交人定向 + 规则附加接收人）。
告警本质是“认领”机制：平台侧把告警确认（`status` 从 `#1#` 未确认变为 `#2#` 已确认/`#3#` 处理中）后才进入消息中心，
未确认/已关闭的告警不产生消息。值班提醒是“定向”机制：值班排班中带班领导（alidpq）或值班人员（多选列 cogxjx，
兼容关系中间表存储形态）命中当前登录人，且排班已进入「值班中」（peuzwi=#cmiu#，即已点击开始值班；待值班阶段不提醒）、
提醒状态未提醒（hfxuuk=#papu#）、值班日期不早于昨日（覆盖跨天夜班）的班次进入消息中心；
消息发送设置（`message-rule-setting.html`，仅系统管理员）中配置值班接收规则的对象作为**附加接收人**，
额外收到近两日值班中的排班提醒（非本人班次，列表 `dutyRole=receiver` 接收人）。
同一班次双侧均命中时只产生一条消息（角色按带班领导优先）。
模型计算为“定向 + 附加”机制：方案主表提交人（created_by）为当前登录人且计算已完成（completed）的方案进入消息中心；
配置模型接收规则的对象作为**附加接收人**，额外收到近 7 天完成的方案通知（不限提交人，含系统自动计算方案；7 天窗防历史全量灌入）。
系统自动计算（防洪预跑/启动恢复）的 created_by 为固定账号，不匹配任何真实用户，对提交人定向天然不产生消息。
已读状态按当前登录人基于消息接收表判定。

### 3.1 未读消息数汇总（角标）

#### 请求

```
GET /h5/message/summary
```

#### 调用示例

```
/hltgq-site/h5/message/summary
```

#### 响应

**进入首页时调用本接口**：后端先同步补建当前登录人可见/可收的消息为未读接收记录（前三类按接收规则可见性——告警含站点范围；值班提醒/模型计算为原有定向 + 规则附加接收人；幂等，绝不重复、不回滚已读状态，30 秒防抖），再统计未读数，保证红点实时准确。
未读数基于消息接收表按当前登录人统计（`is_read=#1#`）。

```json
{
  "alertUnread": 3,
  "complaintUnread": 1,
  "suggestionUnread": 0,
  "dutyUnread": 1,
  "modelCalcUnread": 2,
  "totalUnread": 7
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| alertUnread | long | 未读告警数（当前登录人接收记录中未读的已确认/处理中告警） |
| complaintUnread | long | 未读举报投诉数（当前登录人接收记录中未读的） |
| suggestionUnread | long | 未读意见征集数（当前登录人接收记录中未读的） |
| dutyUnread | long | 未读值班提醒数（当前登录人接收记录中未读的） |
| modelCalcUnread | long | 未读模型计算消息数（当前登录人接收记录中未读的） |
| totalUnread | long | 五者之和 |

| 字段 | 类型 | 说明 |
|------|------|------|
| messageId | String | 消息主键（带模块前缀的方案主表 id，如 `short:xxx`，标记已读时原样回传） |
| schemeName | String | 方案名称 |
| module | String | 模块编码：short/long/loss/demand/moisture/allocation/decision（见附录映射） |
| moduleLabel | String | 模块名称（后端权威映射） |
| finishedAt | String | 计算完成时间（方案主表 updated_at，ISO 格式 `yyyy-MM-ddTHH:mm:ss`） |
| isRead | Boolean | 当前登录人是否已读 |

#### 列表通用规则

- 五类列表均按时间倒序（告警按 `time`、投诉/意见按 `created_at`、值班提醒按值班日期 `owcvsv`、模型计算按计算完成时间，id 降序兑底分页稳定）；
- 告警列表口径：`status IN ('#2#', '#3#')`（仅已确认、处理中，未确认/已关闭不进消息中心），无时间窗口限制（全部活跃告警）；
- 值班提醒口径：双侧定向——带班领导（排班表 alidpq）或值班人员（多选列 `cogxjx`，兼容关系中间表形态）命中当前登录人；补建条件为排班已进入「值班中」（`peuzwi=#cmiu#`，即已点击开始值班）、提醒状态未提醒（`hfxuuk=#papu#`）且值班日期 ≥ 昨日（覆盖跨天夜班，过去的班次不再提醒）；消息发送设置中命中值班接收规则的登录人作为附加接收人，按同一条件额外补建、不限本人班次（`dutyRole=receiver`）；同一班次双侧命中只建一条接收记录（id = `用户id_排班id`）；
- 模型计算口径：定向到方案提交人本人（方案主表 created_by = 当前登录人），补建条件为计算已完成（status 纯值 `completed`，墒情主表为平台字典 `#2#`）且未删除（del_flag=#2#）；列表按计算完成时间倒序（接收表 created_at 在同步时写入方案完成时间）；系统自动计算（防洪预跑/启动恢复）created_by 为固定账号，不匹配任何真实用户，对提交人定向不产生消息；消息发送设置中命中模型接收规则的登录人作为附加接收人，额外补建近 7 天完成的方案（不限提交人，含系统自动计算方案；7 天窗防首次配置灌入历史全量）；
- 列表只返回当前登录人的接收记录（前三类按部门/岗位/角色/人员规则决定可见范围，告警再叠加站点范围：命中规则 site_id 合并为站点范围、任一为空=不限站点）；page 接口内部同样先按需同步再查询（深链接直达列表数据也正确）；`isRead` = 接收记录 `is_read=#2#`；
- 无数据时返回 `total=0`、`pages=0`、`records=[]`。

### 3.5 同步机制与部署注意

**同步模型**：无定时任务、无后台推送；summary/page 被调用时按需补建当前登录人的接收记录（NOT EXISTS 幂等、Redis 30 秒防抖），
消息延迟 ≤ 30 秒（与值班提醒一致）。

**接收规则（消息发送设置）专项**：

| 项 | 说明 |
|------|------|
| 规则来源 | 规则表 `t_auto_hltgq_water_message_rule`；维护页面 `message-rule-setting.html`（仅系统管理员）、接口前缀 `/message-rule`，契约见《消息发送设置.md》 |

**模型计算消息专项**：

| 项 | 说明 |
|------|------|
| 定向口径 | 方案主表 `created_by` = 当前登录人且计算已完成（status 纯值 `completed`；墒情主表为平台字典 `#2#`）且 `del_flag=#2#` |
| 数据来源 | 7 张方案主表 UNION ALL（short/long/loss/demand/moisture/allocation/decision，墒情主表表名为 `t_auto_hltgq_water_moisture_detail`） |

| 规则附加接收人 | 消息发送设置中命中模型接收规则的登录人，额外补建近 7 天完成的方案（不限提交人、含系统自动预跑/恢复方案） |

**值班提醒专项**：

| 项 | 说明 |

#### 计算规则

```
1. 数据源：巡检计划表 t_auto_hltgq_water_patrol_schedule（corp_code=hltgq）
2. 可见范围：仅当前登录人被指派的计划（p."user" = 当前登录人）；他人计划一律不返回，也无法调用点位接口
3. 基础口径：status IN ('#2#','#3#')（已发布/已完成；草稿 #1#、已取消 #4# 永不返回——注意与统计口径含 #4# 不同）
4. 展示态推导：存储 #2#（已发布）按该计划下是否存在**巡检记录**判断——
   无记录=未开始 #5#；有记录=进行中 #2#；存储 #3# 已完成原样返回（人工终态优先）；
   开始巡检接口（§5.3）会写入一条草稿占位记录，因此调用成功后即展示为进行中
5. 筛选：name 对 title 模糊（LIKE %name%）；status 支持中文（未开始/进行中/已完成）与编码（#5#/#2#/#3#）
   双写法，按展示态过滤（「未开始」=已发布且无记录，「进行中」=已发布且有记录），基础白名单恒生效；非白名单值返回 400
6. 排序：按计划开始时间倒序（同时间按 id 倒序）；分页 LIMIT/OFFSET（total 与列表同条件统计）
7. 扩展字段：creatorName 关联用户表 t_apaas_uc_user（p.created_by = u.id）；started = 是否存在巡检记录；
   rangeStationIds 取巡查范围关系表 t_auto_hltgq_knc3g_nlbdju_tkwovk_rel 按 biz_id 聚合（rel_id 即站点ID，逗号分隔，按 nature_order 顺序）；
   draftRecordId = 该计划下最早一条空白占位草稿 id（status = '#1#' 且 site/"_d_10497_device"/result/content 全空），
   无空白草稿时为 null
8. 关联点位 stations：当前页计划 id 一次 IN 查询关系表，左联站点档案表 t_auto_hltgq_5nw74_vnqqef
   实时取名称（zzkaec）与经纬度（bviiio_x/bviiio_y），按 nature_order 顺序分组；无范围关系为空数组，
   坐标未填 lon/lat 为 null（与第四节 /station-data/coords 同口径）
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| 不传任何参数 | 返回本人全部未开始 + 进行中 + 已完成计划的第 1 页（默认 10 条） |
| status 传草稿（#1#）/已取消（#4#）/已逾期/未知值 | 400 `状态筛选仅支持 未开始/进行中/已完成` |
| 仅传 name | 在本人全部展示态（未开始/进行中/已完成）计划中按名称模糊过滤后分页 |
| 计划未指派巡检人 / 指派给他人 | 不返回（他人计划不可见） |
| name 匹配不到 | 返回空分页（total=0、pages=0、records=[]） |
| page 超出总页数 | records 返回空数组（total/pages 正常返回） |
| size 超过 100 | 按 100 生效（响应 size 回显生效值） |
| page/size 传 0 或负数 | 按默认值生效（page=1、size=10） |
| 计划无创建人 / 无巡查范围关系 | creatorName / rangeStationIds 返回 null；stations 返回空数组 |
| 关联站点未填坐标 | 对应 stations 元素 lon/lat 为 null（前端自行跳过） |
| 关联站点已删（档案不存在） | 对应 stations 元素仅 id 有值，name/lon/lat 为 null |
| 计划刚开始巡检、尚未填明细 | draftRecordId 返回占位草稿 id，started=true |
| 占位草稿已被填充（已用 recordId 更新过）或已提交 | draftRecordId 为 null（不再是空白草稿） |

### 5.2 计划关联点位查询

### 5.3 开始巡检

巡检人员本人点击「开始巡检」时调用：服务端校验计划归属与状态后写入一条**草稿占位记录**，计划随即在列表中展示为「进行中」（展示态按计划下是否存在巡检记录推导，§5.1）。**替代 H5 直连低代码表单新增巡检记录**，避免构造计划 id 绕过归属校验（他人计划不可开始），记录巡检人固定为当前登录人。

#### 请求

```
POST /h5/patrol-schedule/start
```

请求体（JSON）：

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| scheduleId | String | **是** | 巡检计划 id（列表行 `id`） |

#### 调用示例

```
POST /hltgq-site/h5/patrol-schedule/start
Content-Type: application/json

{ "scheduleId": "0pfvTtP9xNsQ" }
```

#### 响应

```json
{
  "recordId": "0pkvTtR7yNsQ8gQvyi",
  "scheduleId": "0pfvTtP9xNsQ",
  "started": true,
  "statusCode": "#2#",
  "statusLabel": "进行中"
}
```

#### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| recordId | String | 巡检记录 id（本次写入的草稿占位记录；已开始时为计划下最早一条记录）。该值 = 列表行 `draftRecordId`，后续更新/提交必须使用它 |
| scheduleId | String | 巡检计划 id |
| started | Boolean | 是否已开始巡检（恒为 true） |
| statusCode | String | 计划展示态编码（固定 #2# 进行中） |
| statusLabel | String | 计划展示态名称（后端权威映射） |

#### 计算规则

```
1. 归属：仅当前登录人被指派（计划主表 "user"）的计划可开始；不存在/未指派给当前登录人 → 400
2. 状态：仅已发布 #2# 可开始；草稿 #1# → 400「未发布」，已完成 #3# → 400「已完成」，已取消 #4# → 400「已取消」
3. 幂等：计划下已存在巡检记录（已开始）直接返回最早一条记录 id，不重复写入；
   写 SQL 带 NOT EXISTS，重复调用同一计划不会重复落记录
4. 占位记录字段：patrol_schedule=计划 id、"user"=当前登录人（前端不可指定）、time=当前时间、
   status='#1#' 草稿（不计入已提交统计）、site/设备/result/content 留空；
   created_by/updated_by=当前登录人，created_at/updated_at=当前时间
5. 返回后列表展示态由「未开始」变为「进行中」；后续巡检明细（站点/设备/结果/内容/照片）
   必须用返回的 recordId 调用 /patrol-record/update 更新该草稿，再调 /patrol-record/submit 提交，
   **不得另建记录**（统计口径仅算已提交 status='#2#'，草稿不参与）
6. 幂等兜底（任何客户端）：新增记录入口（/patrol-record/create、计划页「添加巡检记录」）
   若该计划下存在空白占位草稿，则优先「认领填充」该草稿（带四项全空条件的条件更新，
   并发被抢先时退回新增），保存/提交成功后清理同计划其余空白草稿——任何客户端都不会
   再产生「草稿 + 正式」两条；巡检记录列表与计划「巡检记录」弹窗均不展示空白占位草稿
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| scheduleId 缺失/空串 | 400 `巡检计划 id 不能为空` |
| 计划不存在 / 未指派给当前登录人 | 400 `巡检计划不存在或未指派给当前登录人` |
| 计划未发布（草稿） | 400 `巡检计划未发布，不能开始巡检` |
| 计划已完成 | 400 `巡检计划已完成，不能开始巡检` |
| 计划已取消 | 400 `巡检计划已取消，不能开始巡检` |
| 重复开始（已有记录） | 200，返回原记录 id（不重复写入） |
| 未登录 | 401（拦截器统一处理） |

> 不校验计划起止日期：H5 列表本身不按日期过滤，已发布计划均可开始。

### 5.4 新增巡检问题（PC / H5 共用）

约束规则：

```
1. 站点必填且必须等于响应中的 siteId（PC 只读、create 强校验），否则 400「所属站点须与巡检记录一致」
2. 记录缺少站点（开始巡检占位草稿且未补录）→ siteId=null；PC 页面禁止上报，create 返回 400「巡检记录缺少站点，请先补录巡检记录后再上报问题」
3. 设备：候选限该站点（GET /patrol-schedule/devices?siteId=），默认= deviceId，可改为同站点其他设备
4. 记录不存在/已删除 → 400「巡检记录不存在：xxx」
```

#### 计算规则

```
1. code：QST- + 毫秒时间戳（与存量数据同形态），生成后查重，重复则重试（最多 5 次）
2. id/审计列：id 为服务端生成主键；created_by/updated_by=当前登录人，created_at/updated_at=当前时间
3. time（发现时间）：服务端当前时间（只读，前端不可指定）
4. handle_status=#1#（待确认，只读默认）；status=#1#（待处理，表单隐藏但有列）
   编码：handle_status #1# 待确认/#2# 转工单/#3# 直接处理；status #1# 待处理/#2# 处理中/#3# 已转工单/#4# 已关闭/#5# 已作废
5. 关联：site → 站点 id，device → 设备 id，"user" → 发现人 id，abqezf → 巡检记录 id，risk_level → #1#/#2#/#3#
6. 照片：整单事务，按 photoIds 顺序回填 issue_id/nature_order；任一照片不存在/非本人上传/已绑定 → 400 并整体回滚
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| title/siteId/content 缺失或为空 | 400（`问题标题不能为空` / `所属站点不能为空` / `问题描述不能为空`） |
| title > 200 字 / content > 500 字 | 400 提示超长 |
| 站点不存在 | 400 `所属站点不存在：xxx` |
| 设备不属于所选站点 | 400 `所选设备不属于该站点` |
| 发现人用户不存在 | 400 `发现人不存在：xxx` |
| recordId 不存在 | 400 `关联的巡检记录不存在：xxx` |
| siteId 与巡检记录站点不一致 | 400 `所属站点须与巡检记录一致` |
| 关联记录缺少站点（数据异常） | 400 `巡检记录缺少站点，请先补录巡检记录后再上报问题` |
| riskLevel 非法编码 | 400 `风险等级无效（应为 低风险/中风险/高风险）` |
| photoIds 超过 9 张（去重后） | 400 |
| 照片不存在 / 非本人上传 / 已提交过 | 400 `现场照片不存在或已失效，请重新上传` 或 `现场照片不可用（非本人上传或已提交），请重新上传` |
| 上传非图片 / 单张 > 10MB | 400 `仅支持图片格式（jpg/jpeg/png/gif/bmp/webp）` / `单张照片不能超过 10MB` |
| 未登录 | 401（拦截器统一处理） |

> 端到端顺序（H5）：开始巡检取 recordId（§5.3）→ `GET /patrol-issue/record-context` 取站点/设备默认值与站点范围 → 逐张上传照片 → `POST /patrol-issue/create` → 用返回 `code` 提示成功。PC 抽屉流程与本接口完全一致，仅入口不同（页面只传 recordId）。
> 部署前置：需执行建表脚本 `patrol-issue-ddl.sql`（或在 `init.sql` 第 6 节中创建 `t_auto_hltgq_water_patrol_issue_photo`），否则照片上传/读取报错；文件落盘目录由 `hltgq.file-dir` 指定（容器内 `/app/file-dir`，需持久化挂载）。

### 计算规则

```
1. 饼状图：年度区间内最新已完成配水方案（t_auto_hltgq_water_allocate_record status='completed' 且未删除，
   created_at 落在区间内，按创建时间倒序）的旬明细（t_auto_hltgq_water_allocate_tenday）
   三列供水来源求和：塘坝可供水量 / 水厂供水 / 花凉亭水库灌溉供水
2. 列表：年度已确认用水计划（t_auto_hltgq_yn8cm_hjwwcb，plsuub='#1#' 年度、byihlu='#ikok#' 已确认，
   当年最新一条）× 四县：分配水量 = 该县计划量（万m³）；执行进度 = 实际供水量 ÷ 分配水量 × 100
   实际供水量口径与 /irrigation-water/summary 完全一致（宿松=章大计量闸、怀宁=太怀干渠长喉槽、
   望江=南/北干渠进水闸、太湖=渠首进水闸总量扣减）；站点无数据时供水量为 null 不做估算
3. 已完成灌溉 = 四县实际供水量合计（万m³，3 位截断；业务定稿：水量口径，前端文案改「已完成供水 XX 万m³」，不做面积换算）
4. 四卡片灌溉面积：年度内最新已完成需水方案的支渠明细（t_auto_hltgq_water_demand_branch_detail）
   按支渠名去重后按片区求和（亩），片区归县（宿松=太宿干渠、怀宁=太怀灌区、望江=南+北干渠、太湖=总干渠）÷ 10000
5. 数值精度：实际供水量/已完成灌溉 3 位截断（累计流量口径，与灌溉用水接口同口径）；
   分配水量（年度用水计划表单值）/面积 2 位截断、进度 1 位截断
```

### 契约约定（前端联调 2026-09-15 定稿）

1. **空值语义**：progress / finishedVolume / irrigationArea 为 null 即「缺失/未接入」，**后端绝不替换为 0**；
   前端 null 展示「--」，柱状图断点（勿用 Number(x)||0）。唯一例外：distribution 固定三项、
   配水方案存在但无旬明细行时三项 value 为 0.00（无方案时整体空数组）。
2. **映射规则**：distribution 文案与颜色按 code 精确匹配（pond/waterworks/reservoir），不按数组下标；
   主题内置文案（地下水/河道提水/水库供水）与颜色由前端自行映射到 code，后端不返回颜色。
3. **四块恒返回**：缺数据时 distribution/allocationList 为空数组、卡片为 null 或固定值，整个接口不会 502
   （登录失败除外）；前端可进页面拉一次、两个 Tab 共用。
4. **行政区**：district 后端已排好固定四县顺序，且 code 稳定（susong/huaining/wangjiang/taihu），两者均可作唯一键。

### 边界场景

| 场景 | 表现 |
|------|------|
| 年度区间内无已完成配水方案 | distribution 返回空数组 `[]` |
| 年度无已确认用水计划 | allocationList 空数组（即使有需水方案） |
| 无已完成需水方案 | allocationList 各行 progress 为 null；countyDetails 仍返回固定四县行（irrigationArea/finishedVolume 均为 null）；totalArea 仍为 105.83、finishedVolume 为 null |
| 某县设备未接入/窗口内无流量数据 | 该县 progress 与 finishedVolume 为 null（不估算），其余县正常；前端展示「--」 |
| 配水方案无旬明细行 | 三项 value 均为 0.00 |
| 需水方案无支渠明细 | countyDetails 各行 irrigationArea 为 null |
| startDate/endDate 非法或未传 | 缺省本年度区间（非法格式记 warn 日志） |

## 八、工单处理结果（含附件）

工单处理页（列表 → 查看/处理弹窗）所需的列表、详情、附件上传下载移除、填写处理结果与提交验收。
接口前缀为 `/work-order`，与 PC 管理端 `work-order-list.html` **完全共用**（不在 `/h5` 下），鉴权方式与其他接口一致（`X-Session-Id` 头或 Cookie）。

> **与既有附件模块的关系**：应急 / 盘点 / 节水 / 用水计划 / 工单 / 巡检照片各自的附件上传一直是独立的 `/{模块}/attachment/upload`，
> 后端**没有**抽出通用附件接口。原因是各模块附件表不同（本模块为 `t_auto_hltgq_water_work_order_attachment`）、
> 归属字段也不同（本模块为 `order_id`），要做统一接口必须先统一存储模型（单表 + 业务类型/业务 id），属存量重构，暂不做。
> 但底层文件操作已全部收敛到同一工具类：白名单一致（图片 / PDF / Word / Excel 共 11 种扩展名）、单文件 20MB、
> 目录按 `file-dir/{模块}/{yyyy-MM}/` 分月归档，所以**前端封装一套上传组件即可复用到各模块**，只是路径前缀不同。

> **附件数据存什么**：业务主表（`t_auto_hltgq_water_work_order`）**没有任何附件列、不存 fileId**。
> 每个附件在附件表独立一行，保存 `id` / `order_id`（归属工单，上传时为空）/ `file_name` / `file_path`（相对路径）/
> `file_size` / `file_ext` / `corp_code` / 操作人 / 时间；文件本体在磁盘，库里只存相对路径。
> 前端拿到的 `id` 是附件行主键，`attachmentIds` 只是「保存时声明保留哪些附件」的指令，并非写入工单表的字段。

### 8.3 附件上传

单文件上传。**上传即落盘 + 插行**，此时附件不归属任何工单（`orderId` 为空），保存处理结果时才绑定（§8.6）。

#### 请求

```
POST /work-order/attachment/upload
Content-Type: multipart/form-data
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| file | File | **是** | 表单字段名固定为 `file`；单文件，不可一次传多个 |

#### 调用示例

```js
const fd = new FormData();
fd.append('file', fileInput.files[0]);
const vo = await fetch('/hltgq-site/work-order/attachment/upload', {
  method: 'POST',
  credentials: 'include',
  body: fd            // 不要手动设置 Content-Type，浏览器会自动带 boundary
}).then(r => r.json());
// vo.id 即附件主键，先收进本地清单，保存处理结果时放进 attachmentIds
```

#### 响应

```json
{
  "id": "0pavTtA1xNsQ8gQvyi",
  "orderId": null,
  "fileName": "维修前后对比.jpg",
  "fileSize": 358400,
  "fileExt": "jpg",
  "filePath": null
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| id | String | 附件主键，后续放进 `attachmentIds` 或用于移除 |
| orderId | String | 恒为 null（尚未绑定工单） |
| fileName | String | 清洗后的原始文件名（超 120 字符或含非法字符会被截断/替换） |
| fileSize | long | 文件大小（字节） |
| fileExt | String | 扩展名（小写，无点） |
| filePath | String | 恒为 null |

#### 计算规则

```
1. 校验文件非空 → 文件名清洗（去路径段、去控制字符、限长 120 字符）
2. 扩展名白名单：jpg/jpeg/png/gif/bmp/webp/pdf/doc/docx/xls/xlsx（11 种，大小写不敏感）
3. 存储路径：file-dir/work-order/{yyyy-MM}/{uuid}_{清洗后原名}（按上传月份分目录）
4. 先写文件，再插附件行（order_id 为空）；插行失败会回删已写文件，不留孤儿
5. 全局 multipart 限制：单文件 20MB、整个请求 25MB（Spring 全局配置，非本接口独有）
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| file 字段缺失 / 空文件 | 400 `上传文件不能为空` |
| 扩展名不在白名单（如 zip、txt、rar） | 400 `不支持的文件类型（仅支持图片、PDF、Word、Excel）：xxx` |
| 文件超过 20MB | 500（Spring multipart 超限，无业务文案）→ **前端必须先在本地拦掉**并提示「超过 20MB 上限」 |
| 未登录 | 401（拦截器统一处理） |
| 上传成功但用户随后取消 | 前端必须调 §8.5 移除，否则留下孤儿文件与孤儿行 |

### 8.4 附件下载

返回二进制文件流（不是 JSON）。若前端把 sessionId 放在 `X-Session-Id` 头里，必须用 `fetch` + `blob` 接收（`window.open` 带不上自定义头）；若依赖 Cookie 登录态，也可直接 `window.open`。

#### 请求

```
GET /work-order/attachment/download
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:--:|--------|------|
| id | String | **是** | — | 附件主键（详情 `attachments[].id`） |

#### 调用示例

```js
const res = await fetch(API + '/work-order/attachment/download?id=' + encodeURIComponent(id),
  { credentials: 'include' });
if (!res.ok) {
  const err = await res.json();          // 失败时才是 JSON
  showToast(err.message || '下载失败', true);
  return;
}
const blob = await res.blob();
const a = document.createElement('a');
a.href = URL.createObjectURL(blob);
a.download = fileName;                   // 用详情里的 fileName，不要解析响应头
a.click();
URL.revokeObjectURL(a.href);
```

#### 响应

成功：`200`，`Content-Type` 按扩展名推断（图片/PDF/Word/Excel），`Content-Disposition: attachment; filename="<ASCII 兜底>"; filename*=UTF-8''<URL 编码原名>`，body 为文件字节流。

失败：`400` + JSON `{ "message": "..." }`。

#### 计算规则

```
1. 按 id 查附件行（含 file_path），不存在 400
2. 相对路径做目录穿越校验后读取磁盘文件
3. 文件名走 RFC 5987 双写：filename=ASCII 兜底 + filename*=UTF-8''URL 编码（中文名不乱码）
4. Content-Type 由扩展名映射，未知类型按 application/octet-stream
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| id 缺失/空串 | 400 `附件 id 不能为空` |
| 附件行不存在/已删 | 400 `附件不存在或已删除` |
| 附件行在、磁盘文件已被清理 | 400 `附件文件不存在，可能已被清理` |
| 附件属于其他工单 | 不校验归属，只要 id 存在即可下载（登录态内可用） |

### 8.5 附件移除

仅用于**未归属附件**（上传后尚未保存就取消）。已保存到工单的附件不能直接删，必须在保存处理结果时通过 `attachmentIds` 排除。

#### 请求

```
POST /work-order/attachment/remove?id=<附件id>
```

注意：`id` 是 **query 参数**，不是 JSON body。

| 参数 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| id | String | **是** | 附件主键 |

#### 调用示例

```js
await fetch(API + '/work-order/attachment/remove?id=' + encodeURIComponent(id),
  { method: 'POST', credentials: 'include' });
```

#### 响应

```json
{ "success": true }
```

#### 计算规则

```
1. 按 id 查附件行，不存在 400
2. DELETE ... WHERE id=? AND corp_code='hltgq' AND order_id IS NULL
   （带未归属守卫：并发被绑定后返回 0 行 → 拒绝移除，且不删文件）
3. 删行成功后 best-effort 物理删文件（删除失败仅告警，不回滚）
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| id 缺失/空串 | 400 `附件 id 不能为空` |
| 附件不存在/已删 | 400 `附件不存在或已删除` |
| 附件已保存到工单（order_id 有值） | 400 `附件已保存到工单，不能直接移除` |
| 重复调用（已删过） | 400 `附件不存在或已删除`（前端可忽略） |

### 8.6 填写处理结果

仅**处理中**（`statusCode=#2#`）的工单可填写，可重复保存（覆盖 `result` 与处理时间），**不改状态**。

#### 请求

```
POST /work-order/result
Content-Type: application/json
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| id | String | **是** | 工单主键 |
| result | String | **是** | 处理结果，≤1000 字（前后空白会被 trim，trim 后不能为空） |
| attachmentIds | Array\<String\> | 否 | 要保留的附件 id 集合；**不传或 null = 不调整现有附件**；传 `[]` = 清空本工单全部附件 |

#### 调用示例

```js
await fetch(API + '/work-order/result', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    id: orderId,
    result: resultText,
    attachmentIds: list.map(a => a.id)    // 详情已存 + 本次新上传，全部放进来
  })
});
```

#### 响应

```json
{ "success": true }
```

#### 计算规则

```
1. 校验 id / result（trim 后非空、≤1000 字）
2. 条件更新：仅 status='#2#' 的工单可写（0 行 → 400 提示刷新），同时写 result 与 pyxcen（处理时间=保存时刻）
3. attachmentIds 为 null → 完全不动附件，直接返回
4. attachmentIds 非 null → 以集合为准：
   a. 逐个去空、去重；附件行不存在 → 400
   b. 已被其他工单占用 → 400；尚未归属 → UPDATE 回填 order_id（0 行 → 400 提示刷新）
   c. 再查本工单现有附件，凡不在集合内的 → 删行，文件在事务提交后物理删除
5. 整个过程在同一事务内；任一步失败全量回滚，文件不丢
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| id 缺失 | 400 `工单 id 不能为空` |
| result 缺失/全空白 | 400 `处理结果不能为空` |
| result 超 1000 字 | 400 `处理结果不能超过 1000 字` |
| 工单不是处理中（待指派/已关闭/已取消） | 400 `仅处理中的工单可填写处理结果，状态已变化，请刷新后重试` |
| attachmentIds 里有已被删的附件 id | 400 `附件不存在或已移除：xxx`（整个保存失败，前端应重新拉详情） |
| attachmentIds 里有别的工单的附件 | 400 `附件已被其他工单占用：xxx` |
| attachmentIds 传 `[]` | 本工单已存附件全部删除（文件事务提交后清理） |
| 不传 attachmentIds | 附件保持不变（旧调用兼容） |

**前端交互口径（重要，直接决定会不会误删附件）**：

1. **详情未同步成功时禁止保存**：打开处理弹窗必须先拉 §8.2 详情，`attachments` 到手后才允许点保存；否则以空集合提交会把该工单已有附件全部删掉。
2. **附件上传中禁止保存**：存在未完成的 `upload` 请求时拦截保存，提示「附件上传中，请稍候」；否则刚上传的附件 id 还没进清单，保存后它就成了孤儿。
3. **移除新上传的附件 → 立即调 §8.5**：本地清单里 `orderId` 为 null 的项（本次刚上传、未保存），点删除时直接调 remove 接口并同时从清单移除。
4. **移除已保存的附件 → 只改本地清单**：`orderId` 有值的项，点删除只从清单里去掉，**不要**调 remove（会 400）；等保存时靠 `attachmentIds` 排除，由后端删行删文件。
5. **关闭/取消弹窗要清理新上传**：把本次新上传且未保存的附件逐个调 §8.5 移除；已保存的不要碰。若用「取消」按钮关弹窗，清理完再关。
6. **上传响应晚于弹窗关闭**：请求返回时若弹窗已关闭（或已切换工单），立刻对返回的 id 调 §8.5 移除，避免孤儿。
7. **保存成功后重置待清理清单**：保存成功即视为全部归属本工单，再关弹窗不能再当「新上传」清理（否则会把刚保存的附件删掉）。

### 8.7 提交验收

仅**处理中且已填写处理结果**的工单可提交，成功后状态置为**已关闭**，并同步关闭关联问题记录。

#### 请求

```
POST /work-order/submit-accept
Content-Type: application/json
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| id | String | **是** | 工单主键 |

#### 调用示例

```js
await fetch(API + '/work-order/submit-accept', {
  method: 'POST',
  credentials: 'include',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ id: orderId })
});
```

#### 响应

```json
{ "success": true }
```

#### 计算规则

```
1. 条件更新：仅 status='#2#' 且 result 非空的工单可提交（0 行 → 400 提示刷新）
2. 成功后 status='#3#' 已关闭；pyxcen 已有值则保留，缺失时补当前时刻
3. 同步把关联问题（问题表 work_order_id=本工单且 #3# 已转工单）置为 #4# 已关闭（验收闭环）
```

#### 边界场景

| 场景 | 表现 |
|------|------|
| id 缺失 | 400 `工单 id 不能为空` |
| 未填写处理结果 | 400 `仅已填写处理结果的处理中工单可提交验收，状态已变化，请刷新后重试` |
| 状态已变为已关闭/已取消 | 同上 400（前端提示刷新列表） |
| 提交成功后重复提交 | 400（条件更新 0 行） |
| 附件未保存影响提交吗 | 不校验附件；附件只要已保存就在工单下，未保存的与新上传由 §8.6 处理 |

> 说明：8.6 与 8.7 都是「条件更新 + 状态已变即 400」，前端收到这类 400 一律提示「状态已变化，请刷新」并重新拉列表，不要重试原请求。
