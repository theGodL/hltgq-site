# H5 移动端接口文档

> 面向 H5 移动端（巡查统计 / 维修养护统计 / 消息中心 / 站点经纬度批量查询 / 巡检计划列表 / 水资源概览 / 人员信息），生产环境路径统一加 `/hltgq-site` 前缀
> 全部接口需登录态（未登录由拦截器统一 302/401 处理）
> 数据来源为低代码平台表（schema `qixiao-apaas`）

---

## 设计说明

1. **消息可见性口径**：消息按接收规则（部门/岗位/角色/人员）决定可见范围，只有匹配规则的登录人能看到；某类型未配置规则时全员可见。接收记录由后端在 summary/page 接口被调用时按需同步补建（幂等、不重复），无定时分发；规则收紧时存量接收记录不回滚（已读状态保留）。值班提醒与模型计算不走接收规则表，为定向同步（带班领导 / 方案提交人本人）。
2. **已读口径**：接收记录建立时为未读（`is_read=#1#`），登录人阅读后更新为已读（`#2#`）；列表与未读数均基于当前登录人视角返回。
3. **统计口径**：柱状图巡查数按巡检计划统计（排除草稿 `#1#`、含已取消 `#4#`，按计划开始时间 `start_time` 归月）；维修养护饼图仅统计已提交巡检记录（`status=#2#`）；问题记录全状态、按发现时间 `time` 统计。
4. **图表展示口径（配色、堆叠/并列、轴标题）归前端**，后端只返回权威数据（编码 + 数量 + 完整编码映射表）。

## 一、巡查及问题统计（柱状图）

近 12 个月每月巡查任务数（巡检计划口径，含已取消）与问题数量；问题数按风险等级拆分三档，前端按不同颜色绘制（堆叠或并列由前端定夺）。

### 请求

```
GET /h5/patrol-issue-monthly
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:--:|--------|------|
| endMonth | String | 否 | 当前月 | 统计基准月，格式 `yyyy-MM`；返回该月及往前 11 个月（共 12 个） |

### 调用示例

```
/hltgq-site/h5/patrol-issue-monthly
/hltgq-site/h5/patrol-issue-monthly?endMonth=2026-09
```

### 响应

```json
{
  "months": [
    { "month": "2025-10", "patrolCount": 12, "issueCount": 5, "issueLow": 3, "issueMid": 1, "issueHigh": 1 },
    { "month": "2025-11", "patrolCount": 9,  "issueCount": 2, "issueLow": 2, "issueMid": 0, "issueHigh": 0 },
    { "month": "2025-12", "patrolCount": 0,  "issueCount": 0, "issueLow": 0, "issueMid": 0, "issueHigh": 0 }
  ]
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| months | Array | 严格 12 个元素，按月份升序（endMonth 往前 11 个月起），无数据月份补 0，前端 x 轴直接消费 |

**months[].字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| month | String | 月份标签 `yyyy-MM` |
| patrolCount | long | 该月巡查任务数（巡检计划数：排除草稿 `#1#`、含已取消 `#4#`） |
| issueCount | long | 该月问题总数（全状态，含未标注风险等级的记录） |
| issueLow | long | 低风险（`risk_level=#1#`）问题数 |
| issueMid | long | 中风险（`risk_level=#2#`）问题数 |
| issueHigh | long | 高风险（`risk_level=#3#`）问题数 |

### 计算规则

```
1. 基准月 M = endMonth（默认当前月），窗口 = [M−11个月首日, M+1个月首日)（右开区间，避免月末 23:59:59 精度问题）
2. 巡查：t_auto_hltgq_water_patrol_schedule（巡检计划），status IN ('#2#','#3#','#4#')（排除草稿 #1#、含已取消 #4#），按 start_time（计划开始时间）聚合到月
3. 问题：t_auto_hltgq_knc3g_bpzjoh，全状态，按 time（发现时间）聚合到月，
   并按 risk_level 拆 #1#/#2#/#3# 三档
4. 生成 12 个月完整序列，无数据月份补 0
```

### 边界场景

| 场景 | 表现 |
|------|------|
| 某月无任何记录 | 四项计数均为 0 |
| 问题 risk_level 为 null/未知编码 | 计入 issueCount，不计入 issueLow/Mid/High（三档之和可能小于 issueCount） |
| 巡检计划草稿（status=#1#） | 不计入 patrolCount |
| 已取消计划（status=#4#） | 计入 patrolCount（业务口径：取消的计划仍属巡查任务） |

## 二、维修养护统计（饼状图）

已提交巡检记录按巡检结果 `result` 分组计数，固定返回 6 档。

### 请求

```
GET /h5/inspection-result-stats
```

| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|:--:|--------|------|
| startTime | String | 否 | 不限 | 巡检时间起（含）`yyyy-MM-dd HH:mm:ss` |
| endTime | String | 否 | 不限 | 巡检时间止（含）`yyyy-MM-dd HH:mm:ss` |

### 调用示例

```
/hltgq-site/h5/inspection-result-stats
/hltgq-site/h5/inspection-result-stats?startTime=2026-01-01+00:00:00&endTime=2026-12-31+23:59:59
```

### 响应

```json
{
  "total": 100,
  "items": [
    { "name": "#1#", "label": "待填写", "value": 2 },
    { "name": "#2#", "label": "正常",   "value": 60 },
    { "name": "#3#", "label": "异常",   "value": 10 },
    { "name": "#4#", "label": "隐患",   "value": 8 },
    { "name": "#5#", "label": "缺陷",   "value": 5 },
    { "name": "#6#", "label": "故障",   "value": 15 }
  ]
}
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| total | long | 已提交巡检记录总数 |
| items | Array | 固定 6 档（#1#~#6#），无数据的档 value=0 |

**items[].字段：**

| 字段 | 类型 | 说明 |
|------|------|------|
| name | String | 巡检结果编码 |
| label | String | 巡检结果名称（后端返回权威映射） |
| value | long | 该结果的巡检记录数 |

### 计算规则

```
1. 巡检：t_auto_hltgq_water_inspection_record，status='#2#'（已提交，排除草稿）
2. 按 result 分组计数：#1# 待填写、#2# 正常、#3# 异常、#4# 隐患、#5# 缺陷、#6# 故障
3. 缺档补 0，固定按编码升序返回
```

## 三、消息中心

消息由五类数据源组成：**告警**（已确认、处理中）、**举报投诉**、**意见征集**、**值班提醒**（带班领导定向）、**模型计算**（提交人定向）。
告警本质是“认领”机制：平台侧把告警确认（`status` 从 `#1#` 未确认变为 `#2#` 已确认/`#3#` 处理中）后才进入消息中心，
未确认/已关闭的告警不产生消息。值班提醒是“定向”机制：值班排班中带班领导（alidpq）为当前登录人、
提醒状态未提醒（hfxuuk=#1#）且值班日期含今日及以后的班次进入消息中心，不走接收规则表。
模型计算同为“定向”机制：方案主表提交人（created_by）为当前登录人且计算已完成（completed）的方案进入消息中心，
不走接收规则表；系统自动计算（防洪预跑/启动恢复）的 created_by 为固定账号，不匹配任何真实用户，天然不产生消息。
已读状态按当前登录人基于消息接收表判定。

### 3.1 未读消息数汇总（角标）

#### 请求

```
GET /h5/message/summary
```

#### 调用示例

```
/hltgq-site/h5/message/summary
```

#### 响应

**进入首页时调用本接口**：后端先按接收规则（值班提醒/模型计算为定向，不走规则表）把当前登录人可见的消息同步补建为未读接收记录
（幂等，绝不重复、不回滚已读状态，30 秒防抖），再统计未读数，保证红点实时准确。
未读数基于消息接收表按当前登录人统计（`is_read=#1#`）。

```json
{
  "alertUnread": 3,
  "complaintUnread": 1,
  "suggestionUnread": 0,
  "dutyUnread": 1,
  "modelCalcUnread": 2,
  "totalUnread": 7
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| alertUnread | long | 未读告警数（当前登录人接收记录中未读的已确认/处理中告警） |
| complaintUnread | long | 未读举报投诉数（当前登录人接收记录中未读的） |
| suggestionUnread | long | 未读意见征集数（当前登录人接收记录中未读的） |
| dutyUnread | long | 未读值班提醒数（当前登录人接收记录中未读的） |
| modelCalcUnread | long | 未读模型计算消息数（当前登录人接收记录中未读的） |
| totalUnread | long | 五者之和 |

#### 列表通用规则

- 五类列表均按时间倒序（告警按 `time`、投诉/意见按 `created_at`、值班提醒按值班日期 `owcvsv`、模型计算按计算完成时间，id 降序兑底分页稳定）；
- 告警列表口径：`status IN ('#2#', '#3#')`（仅已确认、处理中，未确认/已关闭不进消息中心），无时间窗口限制（全部活跃告警）；
- 值班提醒口径：定向到带班领导本人（排班表 alidpq = 当前登录人），不走接收规则表；补建条件为提醒状态 `hfxuuk=#1#`（未提醒）且值班日期 ≥ 当日（过去的班次不再提醒）；
- 模型计算口径：定向到方案提交人本人（方案主表 created_by = 当前登录人），不走接收规则表；补建条件为计算已完成（status 纯值 `completed`，墒情主表为平台字典 `#2#`）且未删除（del_flag=#2#）；列表按计算完成时间倒序（接收表 created_at 在同步时写入方案完成时间）；系统自动计算（防洪预跑/启动恢复）created_by 为固定账号，不匹配任何真实用户，不产生消息；
- 列表只返回当前登录人的接收记录（前三类按部门/岗位/角色/人员规则决定可见范围）；page 接口内部同样先按需同步再查询（深链接直达列表数据也正确）；`isRead` = 接收记录 `is_read=#2#`；
- 无数据时返回 `total=0`、`pages=0`、`records=[]`。

### 3.3 标记已读（支持批量）

#### 请求

```
POST /h5/message/read
Content-Type: application/json
```

```json
{
  "messageType": "#1#",
  "messageIds": ["alert-uuid-001", "alert-uuid-002"]
}
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|:--:|------|
| messageType | String | **是** | 消息类型：`#1#` 告警 / `#2#` 举报投诉 / `#3#` 意见征集 / `#4#` 值班提醒 / `#5#` 模型计算 |
| messageIds | Array\<String\> | **是** | 消息主键数组（可单条，单次最多 200 条，超出请用 3.4 全部已读） |

#### 响应

```json
{
  "success": true
}
```

幂等：重复标记已读仅更新同一条接收记录（一人对一条消息只有一条接收记录，重复调用无副作用）。

### 3.4 全部标记已读

#### 请求

```
POST /h5/message/read-all
Content-Type: application/json
```

```json
{
  "messageType": "#1#"
}
```

将当前登录人在该类型下的全部现存消息标记为已读，响应同 3.3（支持 `#5#` 模型计算）。

### 3.5 同步机制与部署注意

**同步模型**：无定时任务、无后台推送；summary/page 被调用时按需补建当前登录人的接收记录（NOT EXISTS 幂等、Redis 30 秒防抖），
消息延迟 ≤ 30 秒（与值班提醒一致）。

**模型计算消息专项**：

| 项 | 说明 |
|------|------|
| 定向口径 | 方案主表 `created_by` = 当前登录人且计算已完成（status 纯值 `completed`；墒情主表为平台字典 `#2#`）且 `del_flag=#2#` |
| 数据来源 | 7 张方案主表 UNION ALL（short/long/loss/demand/moisture/allocation/decision，墒情主表表名为 `t_auto_hltgq_water_moisture_detail`） |
| 提交人写入 | 7 个模型提交接口在主表写入时把 `created_by` 写为当前登录人；系统自动计算（防洪预跑/启动恢复）为固定账号 `model-service`，不匹配任何真实用户，天然不产生消息 |
| 存量数据 | 部署前历史方案 `created_by` 均为固定账号，不回溯产生消息；仅部署后新提交的方案会推送 |
| 性能依赖索引 | 7 张方案主表 `(created_by, status)` 索引 + 接收表 `(user_id, message_type, created_at DESC)` 索引，DDL 见项目 `init.sql`（部署时执行，IF NOT EXISTS 幂等） |
| 列表排序 | 按计算完成时间倒序（同步时把方案完成时间写入接收表 created_at，作为排序键） |

```
   按支渠名去重后按片区求和（亩），片区归县（宿松=太宿干渠、怀宁=太怀灌区、望江=南+北干渠、太湖=总干渠）÷ 10000
5. 数值精度：供水量/分配水量 2 位截断、面积 2 位截断、进度 1 位截断，与灌溉用水接口同口径
```

### 契约约定（前端联调 2026-09-15 定稿）

1. **空值语义**：progress / finishedVolume / irrigationArea 为 null 即「缺失/未接入」，**后端绝不替换为 0**；
   前端 null 展示「--」，柱状图断点（勿用 Number(x)||0）。唯一例外：distribution 固定三项、
   配水方案存在但无旬明细行时三项 value 为 0.00（无方案时整体空数组）。
2. **映射规则**：distribution 文案与颜色按 code 精确匹配（pond/waterworks/reservoir），不按数组下标；
   主题内置文案（地下水/河道提水/水库供水）与颜色由前端自行映射到 code，后端不返回颜色。
3. **四块恒返回**：缺数据时 distribution/allocationList 为空数组、卡片为 null 或固定值，整个接口不会 502
   （登录失败除外）；前端可进页面拉一次、两个 Tab 共用。
4. **行政区**：district 后端已排好固定四县顺序，且 code 稳定（susong/huaining/wangjiang/taihu），两者均可作唯一键。

### 边界场景

| 场景 | 表现 |
|------|------|
| 年度区间内无已完成配水方案 | distribution 返回空数组 `[]` |
| 年度无已确认用水计划 | allocationList 空数组（即使有需水方案） |
| 无已完成需水方案 | allocationList 各行 progress 为 null；countyDetails 仍返回固定四县行（irrigationArea/finishedVolume 均为 null）；totalArea 仍为 105.83、finishedVolume 为 null |

| 配水方案无旬明细行 | 三项 value 均为 0.00 |
| 需水方案无支渠明细 | countyDetails 各行 irrigationArea 为 null |
| startDate/endDate 非法或未传 | 缺省本年度区间（非法格式记 warn 日志） |
